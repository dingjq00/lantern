# Lantern 后续推进路线图

> 制定日期：2026-05-27  
> 依据：当前代码、仓库文档、Git 历史、本地验证和本地已保存的 benchmark 记录。  
> 目标：把已能演示的三系统自然语言查询平台，推进为可稳定评估、可安全交付、可继续扩展的产品底座。

## 1. 核心判断

早期文档的阶段顺序已经被实际开发推进所超越：MES 已接入，系统总数已到 3 个，声明式 skills 已到 30 个，ReAct、数据摘要和平台 benchmark 都已有代码。因此下一阶段不应继续简单标记为“接入更多系统”，而应按以下顺序推进：

1. **先守住安全和工程基线**：清除明文凭据回退、统一配置、让 lint/build/test 成为可靠门禁。
2. **再提升答案可信度**：修复置信度与跨系统总结的结构缺陷，为核心链补回归测试。
3. **随后建立反馈闭环和可观察性**：用户反馈必须能产生可验证的改进，而不是直接污染路由经验。
4. **具备权限与运维能力后再对外试点**：当前系统适合内部验证，不适合直接作为生产入口。
5. **工具规模或业务目标触发时再做动态路由和新系统扩展**。

产品边界建议维持为：近期只承诺**只读查询与分析**；自然语言写操作应等鉴权、授权、审计、确认机制与回滚策略完成后另行立项。

## 3. 关键缺口与优先级

| 优先级 | 缺口 | 代码依据 | 影响 |
| --- | --- | --- | --- |
| P0 | 源码和脚本含凭据回退默认值 | `lib/llm/codex-proxy.ts`、`scripts/*.ts`、`mcp-server/src/eam-api.ts`、`mcp-server/src/jmix-api.ts` | 仓库共享和部署存在直接安全风险，已暴露的凭据应轮换 |
| P0 | Chat 默认工具目录错误 | `app/api/chat/route.ts` 默认 `./tools`，实际目录为 `skills/` | 未配置环境变量时核心功能不能稳定启动 |
| P0 | 工程门禁失效 | lint 当前 124 errors；仅 19 条单测 | 任何 prompt/router/handler 优化都难以安全合并 |
| P0 | 置信度逻辑不可信 | `verdictConfidence` 固定 `medium`，`computeConfidence()` 要求所有信号 `high`；执行成功又不等于结果相关 | 正常查询无法得到 high，错误工具调用也缺少相关性判定 |
| P1 | 跨系统总结只使用首个系统上下文 | `prepareSummarizeContext()` 从第一条结果取 `systemId`，仅应用该系统 domain model/KPI | 正是平台 benchmark 弱项，会削弱跨系统解释质量 |
| P1 | 同工具多次结果在 summarize 前被覆盖 | `dedupMap.set(tool, result)` 仅保留最后一次调用 | 多对象对比或分批查询时可能丢证据 |
| P1 | 反馈未进入改进闭环 | `/api/feedback` 只更新 session；lesson/verdict 未安全接入主流程 | 用户纠错不能推动质量提升 |
| P1 | API 暂无用户身份和授权边界 | API 路由直接使用默认 tenant/user，无登录、权限、限流 | 不满足企业数据平台试点条件 |
| P2 | 工具预筛选未启用 | `ToolRegistry.match()` 存在但路由直接注入全部工具 | 当前 30 工具尚可运行，继续扩展会加重上下文和消歧成本 |
| P2 | 运维与成本指标缺失 | trace 有耗时，但无结构化监控、token/成本/依赖健康治理 | 无法判断生产稳定性和单位查询成本 |

## 4. 目标路线

以下阶段按依赖排序，而不是按功能吸引力排序。每一阶段必须通过验收门槛后，下一阶段的工作才算具备可靠基础。

### R0：安全与可重复基线

**目标**：仓库可以安全共享，新环境可以按文档稳定启动，基础验证成为真实门禁。

**工作项**

| 工作包 | 内容 | 涉及位置 |
| --- | --- | --- |
| 凭据治理 | 移除所有 key/password/secret 回退值；启动时校验必需环境变量；轮换曾写入源码的凭据 | `lib/llm/`、`scripts/`、`mcp-server/src/*-api.ts` |
| 配置统一 | 将工具默认目录统一为 `./skills`；把运行配置和缺少配置的错误提示集中管理 | `app/api/chat/route.ts`、配置辅助模块、`.env.example` |
| 构建可重复 | 处理 Google Fonts 离线/受限网络构建问题；按 Next.js 16 文档消除 workspace root 与 NFT trace 警告 | `app/layout.tsx`、`next.config.ts`、相关服务端文件加载策略 |
| 代码门禁 | 清理现有 lint error；加入 CI 验证 `lint`、`test`、两个 build；决定是否纳入 hooks | eslint/CI 配置及触发问题的代码 |
| 当前改动收口 | 对现有 observation/prompt 跨系统变更单独运行回归并形成清晰提交，不和基础治理混杂 | 当前未提交业务改动 |

**验收门槛**

- 仓库搜索不再找到任何真实凭据或开发账号密码回退。
- `npm test`、`npm run lint`、`npm run build`、`cd mcp-server && npm run build` 全部通过。
- 全新 `.env.local` 配置流程能启动 Web，并能明确提示尚未配置的数据源。
- 当前 prompt 变更有一份独立 benchmark 对比记录。

### R1：核心正确性与回归保护

**目标**：让“选工具、取数据、总结答案、显示置信度”的主链可测试、可解释。

**工作项**

| 工作包 | 内容 | 验证重点 |
| --- | --- | --- |
| Router 单元测试 | 覆盖 `resolveArgRefs` / `navigatePath`、ReAct 轮次、级联、失败降级、循环检测 | 参数引用和错误分支不再依赖手测 |
| Summary/Context 测试 | 覆盖多系统、多次同工具调用、空数据和部分错误 | 不丢证据，不错误套用领域公式 |
| Storage 与 API 测试 | migration 幂等、session/trace/feedback 保存、benchmark API | 评估数据可复核 |
| MCP 契约测试 | YAML 工具名与 server 注册一致；handler 返回统一成功/错误结构 | 错误结果不被当作有效数据计入高置信度 |
| 置信度重构 | 引入“意图覆盖/数据相关性”信号，移除停用 verdict 对 high 的阻塞 | high/medium/low 都有可重现测试样例 |
| 评测基线版本化 | 固化 EAM、EDHR、平台用例版本和结果格式；对 fact/followUp/跨系统分项计分 | 以后优化可以公平比较 |

**验收门槛**

- 核心模块拥有测试：router、summarize-context、confidence、storage、tool registry 至少各一组。
- 错误 handler 返回不会计为成功调用或触发误导性的高置信度。
- 每次修改 prompt/router/handler 均有固定测试集的前后结果。
- 现有 EAM/EDHR 历史水平不退化；平台 benchmark 形成新基线。

### R2：跨系统分析质量

**目标**：将三系统“能调用”提升为“能正确关联和解释”，直接攻克当前平台 benchmark 的弱项。

**工作项**

| 工作包 | 内容 |
| --- | --- |
| 多系统总结上下文 | `prepareSummarizeContext()` 识别全部已调用系统，为每个系统应用适配的 domain model、KPI 和建议规则 |
| 保留多次调用证据 | 按调用或参数维度保留同一工具的多个结果，避免对比/链式查询被最后一次覆盖 |
| 跨系统关系模型 | 明确定义 EAM 设备/产线与 MES 工单/产线的桥接规则，区分可关联事实与仅可提示的分析假设 |
| 跨系统用例扩展 | 从现有 6 道跨系统用例扩展至涵盖设备影响生产、库存影响排产、维护影响产量、质量回溯等场景 |
| 当前 prompt 调优验收 | 将正在进行的“系统覆盖检查”变更纳入本阶段，用控制变量结果决定保留或回退 |

**验收门槛**

- 平台 benchmark 总体 Recall 达到 `>=95%`，跨系统用例 Recall 达到 `>=95%`。
- 跨系统事实断言无编造；涉及因果的回答明确区分“数据证明”与“建议核查”。
- 对至少 10 条真实管理查询进行人工验收，记录错误分类与下一轮改进来源。

### R3：反馈闭环与可观察性

**目标**：把用户使用数据转化为受控的改进信号，同时能回答“系统哪里慢、哪里错、花费多少”。

**工作项**

| 工作包 | 内容 |
| --- | --- |
| 反馈结构化 | thumbs down 后补充错误原因选项；反馈关联 session、实际工具链和回答版本 |
| Lesson 闭环 | 仅将用户反馈或确定性事实失败写入 lesson；注入下一次路由前先有回放测试与过期策略 |
| 自动质量守望 | 将 validator 扩展为可解释的数据/意图契约校验；不直接复活已证明无效的 AI 自评方案 |
| 观测指标 | 记录路由/工具/总结延迟、错误率、重试、token 与模型成本、confidence 分布、用户反馈率 |
| Dashboard | 将 benchmark、线上采样、反馈趋势分开展示，避免把离线得分误当线上正确率 |

**验收门槛**

- 负面反馈能追踪到一次具体回答，并可生成可撤销、可过期的 lesson。
- 任何自动注入经验均有 A/B 或回放验证，不以模型自评分数直接驱动生产路由。
- 有按系统和工具拆分的可靠性、延迟与成本看板。

### R4：企业试点就绪

**目标**：在受控客户/内部团队中提供只读试点服务。

**工作项**

| 工作包 | 内容 |
| --- | --- |
| 身份认证与授权 | 用户登录或企业 SSO；tenant、系统、工具、数据范围权限校验 |
| 数据安全 | trace/日志脱敏，secret 管理，审计导出，数据保留和删除政策 |
| 运行稳定性 | API 限流、超时/重试/熔断、MCP/data-source 健康检查、故障降级 |
| 存储演进 | 明确 SQLite 仅用于本地/小规模场景；试点采用可备份、可并发的生产存储 |
| 交付资料 | 部署 runbook、配置/密钥说明、API 文档、运维告警、灾备方案 |

**验收门槛**

- 未认证用户不能读取业务数据；授权测试覆盖跨 tenant 与跨系统越权。
- 试点环境具备告警、备份、审计和故障恢复流程。
- 发布范围明确为只读查询/分析，用户可见回答包含数据来源与置信提示。

### R5：规模化与新能力

**触发条件**：工具数量超过约 40、Prompt token/延迟明显增长、平台 benchmark 由于工具消歧显著回退，或明确新增 QMS/WMS/写操作需求。

**候选方向**

| 方向 | 启动条件 | 先验证什么 |
| --- | --- | --- |
| Top-K 工具预筛选 | 工具规模导致路由消歧下降 | 与全量工具的 Recall、延迟、成本对比 |
| 动态工具发现/加载 | 多系统下工具数持续增加 | 发现 -> 元数据 -> 执行是否优于扁平注入 |
| 新系统接入 | 有明确业务闭环和数据源负责人 | YAML + handler + domain model + benchmark 全套验收 |
| 自然语言写操作 | 只读试点稳定且具备权限审计 | 人工确认、幂等、审批、撤销和审计，不与查询直接混用 |

## 6. 每类改动的质量门槛

| 变更类型 | 必须验证 |
| --- | --- |
| 文档/配置说明 | `git diff --check`，链接与命令人工核对 |
| UI/API 小改 | `npm test`、`npm run lint`、`npm run build`，必要时浏览器验证 |
| Router/prompt/summarize/confidence | 单元测试 + EAM/EDHR/platform 固定 benchmark + 事实抽检 |
| YAML skill/MCP handler/外部系统接入 | 契约测试 + 对应系统 benchmark + 错误/空结果/权限场景 |
| 鉴权/授权/凭据/生产部署 | 安全审查、越权测试、日志脱敏检查、恢复演练 |

任何历史 benchmark 都只能作为参考；“完成”必须基于变更之后重新运行的证据。

## 7. 文档维护规则

- 本文件记录长期推进路线与阶段完成条件；完成阶段后更新结果与下一阶段决策。
- `docs/handoff.md` 记录当前工作区状态、正在执行的任务和阻塞项。
- 架构重大变更写入新的 decision record，不直接覆盖早期实验结论。
- 评测结果应标明日期、提交 SHA、模型、数据源版本、测试集版本和运行参数。

## 8. 本轮规划后的第一个开发任务

建议第一个实现任务固定为 **R0 凭据与运行配置治理**，原因很简单：它不依赖模型效果，不与当前跨系统 prompt 调优冲突，却决定仓库能否安全协作和部署。该任务完成后，再把当前 prompt 修改纳入新鲜 benchmark 回归，随后开展跨系统总结与置信度修复。
