1 愿景

用户面对一个输入框，用自然语言操作任何企业系统。

不是在现有系统上"加一个聊天窗口"。是从根本上改变人和企业系统的交互方式 —— 从"学会怎么用系统"变成"说你要什么"。

Phase 1

→
Phase 2
主动智能助手
→
Phase 3
企业大脑

C 级平台定位 — 这不是 EAM 的附属品。架构从第一天就为"接入任何有 API 的企业系统"而设计。 EAM 是第一个场景（22 个工具已跑通），但 MES、ERP、QMS、WMS 的接入只是加 YAML + Handler 的工作量。

终极画面：工厂厂长早上打开手机，系统主动说 "早上好，A 线今天有 2 台设备需要保养， B 线昨天故障率偏高建议关注。" 他不需要想问什么 — 系统已经知道他关心什么。

3 智能层深度解析

3.1 六层 Context 架构

Context Engineering 的核心洞察：静态在前（可缓存），动态在后。 Layer 1-4 是全局不变的（不同用户、不同查询共享同一缓存），Layer 5-6 每次请求动态组装。

身份定义 — "你是 Insight68 NL-API 平台的智能引擎"
🔒
2
Rules

底线约束 — 禁止编造、不做 SQL、错误分级处理
🔒
3
Task Instructions
base + react + guide
5 步结构化模板、参数引用语法、工具选择方法论
🔒
4
Examples
few-shot-examples.json
6 个示例覆盖主要多步模式（设备→故障→备件 等）
🔒
CACHE BOUNDARY — Prompt Caching
5

[runtime assembled]
日期映射 + YAML 生成工具描述 + verdict + 用户上下文
🔄
6

[user message]
用户自然语言查询
🔄
为什么这样分层
Layer 1-4 对所有用户、所有查询完全一样，可以被 LLM Provider 的 Prompt Caching 命中（Anthropic/OpenAI 均支持）， 极大降低 token 成本和首 token 延迟。Layer 5-6 是"一次性"内容，每次不同。

3.2 执行引擎 — 三步 Think

T1
think① 规划
5 步结构化模板（ToolGT + Step-Back + Reflexion 融合）：
[意图] 先理解意图，不看工具 — 防关键词劫持
[候选] 列出可能的工具及理由
[审查] 域覆盖检查 — 每个域至少有一个工具
[规划] 确定调用序列，使用 {{N.path}} 参数引用
[验证] 最终确认规划完整性
⇅
级联检查
mini 返回 unsupported / 空 calls → 自动升级 gpt-5.4。 贡献 +16pp recall，是单一最大提升因子。
E1
Router 执行
按序执行 tool calls。自动解析 {{N.path}} 引用，将前一步结果传入后一步参数。 多层依赖一轮完成。
T2
think② 审查放开（Reflexion）
不问 "够不够"（是非判断），问 "有什么字段/缺什么"（事实陈述）。
覆盖 → finish  |  不覆盖 → 放开范围补充调用。
E2
Router 补充执行
如有补充 calls，执行并收集结果。
T3
think③ Finish
确认所有数据已收集，准备进入汇总。简单题跳过此步（2 次 think），复杂题 3 次。
S
Summarize — 反编造护栏
数据不足时说 "数据不足"，不编数字。
输出结构化中间格式 (answer + data + display + columns + followUp)，接入层按端渲染。

→
unsupported 或

自动升级

gpt-5.4
处理困难 case
为什么不直接用 5.4
数据说话：模型从 mini 升级到 5.4 仅 +0.6pp（实验 R2 vs R3）。绝大多数查询 mini 就能搞定。 级联让 95%+ 请求用便宜模型，只有 mini 处理不了的 case 才升级 — 成本最优。

3.4 自学习闭环（目标架构）

自学习的核心难点不是学习算法，是标注 — 怎么知道什么是对的什么是错的。 经过系统性验证，我们否定了两个看起来合理的方案，找到了真正可靠的信号源。

已否决
Verdict 记录 Winner
60% 准确率下积累 40% 错误经验。越学越差。
已否决
AI 自评 Lesson
循环论证 — 同一个脑子犯的错，自评也发现不了。
选定方案
工具返回值即信号
零成本、客观、不依赖 AI 或人的主观判断。有数据+匹配=大概率对，空/不匹配=可能错。
✔ 信号 A：结果质量检测 P1.5
扩展 validator.ts：工具返回数据 vs 用户意图 → 匹配度检测。 空结果检测："真没有" vs "选错工具"。纯规则不用 LLM。 检测到不匹配 → 自动写 lesson（客观事实）。
✔ 信号 B：用户反馈 P1.5
Thumbs down → 记录 query + selectedTools + "bad"。 人工标注正确路径（可选）→ lesson.betterPath。 下次同 intent_hash 查询 → 注入"上次用 X 效果差"。
○ 补充信号 C：高级模型蒸馏 P2
mini 执行后，5.4 异步评估 mini 的选择。和 AI 自评的本质区别：不是同一个模型评自己， 是更强的模型评更弱的 — 信息差保证标注可靠。
○ 补充信号 D：多模型并行 P2
同时跑 2-3 个模型，用户选择哪个就是隐式标注 — 类似 RLHF 偏好机制。 需要真实用户流量，属于上线后积累。
Lesson → 写入经验层 → 下次同类查询自动注入上下文 → 越用越准

4 MCP 工具层架构

4.1 设计哲学

⚙
MCP = 动作
获取数据、执行操作。确定性代码，不含 AI 判断。 "查 A 线设备列表" 就是调 API 拿数据，没有歧义。
🧠
AI = 能力
分析、聚合、推理、对比。不做成 MCP 工具。 "故障率同比" 是 AI 拿到两个月的数据后计算的。
📖
工具描述 = 说明书
YAML 中的 description / when_to_use / when_not_to_use 是 AI 选择工具的唯一依据。描述质量线性决定命中率。
实验验证
8 个方案对比实验证明：Prompt 贡献 99% 的准确率提升，模型贡献 1%。 工具描述写法比模型选择重要 — 这与 UC Berkeley Gorilla/BFCL 的学术发现一致。

4.4 工具扩展的诚实成本

加一个新企业系统 不是零成本。主体工作量是 YAML 声明 + MCP Handler，但 few-shot 编排示例和选择指南的更新不可省略。 方案 A 实验的核心发现：Prompt 中的指南和示例贡献了 99% 的准确率提升。

工作项 估计量 可跳过?
YAML 工具声明文件 每工具 1 文件，~50 行 不可跳过
MCP Server Handler 每工具 1 handler，调 REST API 不可跳过
Few-shot 编排示例 每域 1-2 个多步模式示例 不可跳过 — 不补则新域准确率偏低
工具选择指南更新 该域的路由策略说明 不可跳过
接入层改动 0 —

目标：通过 MCP Server 模板化（通用脚手架 + endpoint 配置），把新系统接入从两周缩到 2-3 天。

7 核心设计原则

以下 8 条原则不是理论推导，是从一整天的实验数据和架构迭代中提炼出来的。每一条背后都有具体的失败案例。

1 MCP 是动作，AI 是能力
聚合/统计/对比是 AI 的分析能力，不做成 MCP 工具。MCP 只做确定性数据获取。
2 Guide 是方法论，YAML 是具象化
guide 零项目特定内容，保持完全通用。项目特定知识全部在 YAML 声明文件中。
3 从错误中学习，信号来自外部
记录正确答案反而没那么重要。有效信号：工具返回值（客观）、用户反馈（thumbs down）、Ground Truth（测试）。AI 自评是循环论证。
4 优化优先级：Prompt > AI 分析 > MCP 工具
Prompt 贡献 99% 的提升。先优化 Prompt 和 guide，再优化 AI 分析策略，最后才动工具。
5 工具描述前置关键信息
在工具描述中自然语言嵌入链路关系。"list 工具不含 X，需要本工具补全。" 描述质量线性决定命中率 — Pinterest 验证。
6 Poka-Yoke 防错设计
工具应同时接受业务编号和内部 ID。让工具难以被错误使用，而不是让 AI 更聪明。
7 Summarize 绝对不能编造
数据不足时说 "数据不足"，不编数字。宁可用户觉得你笨，也不能给错误数字。高层给错一次数字就不会再用。
8 复杂度是输出不是输入
不预判查询复杂度。让引擎自己跑出结果，复杂度由执行链路自然呈现。三步 think + 级联已经够用。
