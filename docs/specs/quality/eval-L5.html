Core Finding

The routing is correct. The tools are chosen correctly. The parameters are reasonable. But the data returned by eam.trend is catastrophically incomplete. Every single trend query across all 6 domains (fault, spare, patrol, anomaly, maintenance, repair) returns at most 1 data point in the time series (typically only "2026-03"), regardless of the requested date range or groupBy.   • No trend can be computed (requires >= 2 time points)
  • No year-over-year comparison is possible (historical periods return empty)
  • splitBy parameter appears to be silently ignored (no productionLine/equipment split in results)
  • The AI correctly identifies data insufficiency but cannot work around a fundamentally broken data layer
ROOT CAUSE: eam.trend MCP Tool Returns Degenerate Data
The eam.trend tool is documented to return [{period, count, ...splitFields}] time series. In practice, it returns a single-element array like [{"period": "2026-03", "count": 108}] for ANY date range, ANY groupBy, ANY splitBy. The "from 5 domains, fetch paginated data and aggregate in MCP layer" approach appears to be aggregating everything into a single bucket. The backend aggregation logic is broken. This is NOT an AI problem -- this is a data pipeline problem.

Root Cause Hierarchy (Priority Order)

P0 -- eam.trend MCP Aggregation is Broken
Impact: Blocks ALL 6 L5 questions. No trend analysis is possible.
Root cause: The MCP layer's in-memory aggregation for non-patrol domains collapses all records into the latest month. Likely bug: date parsing or bucket assignment in the aggregation loop.
Fix: Debug the eam.trend MCP tool's aggregation logic. Verify that records are assigned to the correct month/week/day bucket based on their creation date, not the query date. Add unit tests for multi-month date ranges.
P1 -- splitBy Parameter Silently Ignored
Impact: Blocks comparative analysis (T35 productionLine split, T39 equipment split).
Root cause: The MCP tool accepts the parameter without error but doesn't use it in aggregation.
Fix: Implement splitBy grouping in the aggregation loop. Each split value should produce its own time series. Add tests for splitBy=productionLine and splitBy=equipment.
P1 -- Test Data Lacks Historical Depth
Impact: Even if trend tool is fixed, 2025 data is empty for all domains.
Root cause: Test database only has 2026-03 records. Year-over-year comparisons will always fail.
Fix: Seed test database with 6-12 months of historical data across all domains. Include realistic patterns (seasonal variation, equipment-specific clustering).
P2 -- AI "Partial Answer" Pattern
T38 had enough data to answer half the question. T37 had enough to answer the full question. The summarize step should be trained/prompted to deliver what it CAN, not refuse entirely when one dimension is missing. Add to system prompt: "If you can answer part of the question with available data, do so. Clearly label which parts are answered and which need more data."
P2 -- Skill YAML / Tool Schema Alignment
maintenance.search and anomaly.search have limited groupBy enums, but the AI tries productionLine and month which don't exist. Either expand the tool's groupBy options or update the Skill YAML's when_to_use to NOT promise productionLine grouping.
P3 -- Display Mode: Trend Questions Should Default to Chart/Table
All 6 questions returned display: "text". Trend analysis questions should trigger chart or table display mode. Even empty data is better shown as a table ("No data for Jan, No data for Feb, 108 in Mar") than as a paragraph of text.
P3 -- Confidence Calibration
T39 marked "high" confidence with zero useful data. T37 marked "high" with a year calculation error. Confidence should be LOW when the answer is "data insufficient" or when multiple retries yielded no improvement.
