系统性问题诊断

8 题 L3 全部交出"无法回答"的白卷，但这不是 AI 笨、也不是工具少 — 问题出在三个系统层面。 下面按严重度排序。

1. [P0] Summarize 层与 Thought 层脱节 — 最致命的 bug

T22、T23、T24、T26 这 4 题中，AI 的 Thought 推理过程得出了正确或合理的结论， 但最终 Answer 却输出"无法回答"。这意味着：

  • T22：Thought 说"所有 lowStock=false，没有库存不足" → Answer 说"不包含 BOM 信息"
  • T24：Thought 说"Round 1/2 成功查询，结果为空" → Answer 说"API 错误导致无法获取"
  • T26：Thought 说"总任务3，完成0，执行率0%" → Answer 说"不包含执行率信息"

推断原因：summarize prompt 可能过于保守 — 对"空结果"和"查询失败"不做区分，一律输出保底话术。 另一个可能是 summarize 层优先使用第一个工具的结果，而忽略后续工具的有效数据。

修复建议： (1) summarize 层必须区分"查到了，结果为空集"和"查询失败/数据不足"； (2) 当多轮查询时，以最终有效结果为准，不被早期错误污染； (3) Thought 的结论应该是 Answer 的直接输入源，不应被保底机制覆盖。

2. [P0] Benchmark 测试数据与系统数据不匹配

T27 (WO-005) 和 T28 (EQ-001) 使用了系统中不存在的标识符。 系统设备编号格式是 "EQ202603260144"，维修工单编号是 "RO202603110002"， benchmark 用的 "EQ-001" 和 "WO-005" 完全不匹配。

修复建议： (1) 所有 L3 测试题必须使用系统中真实存在的标识符； (2) 或者在 Resolver 中增加别名映射（如 EQ-001 → EQ202603110001 这种简短别名）； (3) Benchmark 框架应有数据预检步骤，确认测试题引用的实体确实存在。

3. [P1] 跨域关联数据为空 — 让 L3 查询毫无意义

T22 的 equipmentCount=0、T25 的 spareSummary.count=0、所有工单的 knowledgeRefs=[] — 跨域关联字段在测试数据中全部为空值或零值。L3 查询的核心价值在于跨域串联， 但如果关联字段本身没有数据，再好的工具链编排也无法产出结果。

修复建议： (1) 测试数据中必须包含跨域关联 — 至少部分工单要有备件明细、知识引用、出库单； (2) spare 的 equipmentCount 必须正确反映关联设备数； (3) 考虑用种子脚本创建一组完整的跨域测试数据（设备 → 故障 → 维修 → 备件出库 → 知识引用）。

4. [P1] MCP Handler 日期格式不一致

T24 的 anomaly.search 要求完整 ISO datetime（拒绝纯 date）， 而 T23 的 repair.search 接受两种格式。不同 handler 的容忍度不同会导致 AI 摸不清规律。

修复建议：MCP 层统一做日期格式标准化 — 如果收到 "2026-02-28"，自动补充为 "2026-02-28T00:00:00"（from）或 "2026-02-28T23:59:59"（to）。

5. [P2] AI 在标识符不匹配时缺乏用户引导

T27 和 T28 中，AI 知道用户给的标识符不存在，但没有展示候选列表让用户选择。 T27 Round 2 甚至自作主张选了一个不相关的工单。 正确做法是展示搜索结果供用户确认，而非替用户决定。

6. [P2] 洋葱泛化策略执行不彻底

T24 去掉了 source 限定但没进一步去掉 productionLine 来验证全局数据。 T21 找到 28 个工单后没有继续查 repair.profile。 泛化的目标是"要么找到数据，要么确认全局都没有"，中途放弃违背了这个原则。
