系统性问题汇总 (按严重程度排序)

  • 致命Benchmark 测试用例使用虚假标识符 — EQ-001/EQ-002/EQ-003/WO-001/SP-001 在真实系统中均不存在。这导致 6 道题注定返回空数据，Recall=100% 毫无意义，因为系统"成功地找不到数据"。这是测试设计问题而非系统问题。
  • 致命AI 回答与 tool 返回数据矛盾 — T18 的 fault.search 返回 total:108，这就是本月新增数量，但 AI 说"无法回答"。T07 dashboard 显示 spareAlerts:2，但 spare.search(lowStock:true) 返回 0 条。数据自相矛盾暴露了 dashboard 与明细工具的口径不一致。
  • 致命dateRange 参数格式不兼容 — T11 首轮用 "2026-02-01"（无时间部分）导致 400 错误，API 要求 LocalDateTime 格式。MCP 层未做格式归一化，将报错直接透传给 AI。
  • 严重search 的 identifier 参数无效 — T03/T13 中 equipment.search 传入 identifier="EQ-001" 但返回的结果仍然是未过滤的全量列表（total:165），说明 search 工具的 identifier 参数未生效或后端未实现模糊搜索。
  • 严重冗余追查轮次普遍 — 20 题中 12 题是 2 轮完成（最优），但 8 题用了 3 轮。多出的轮次大多是"profile 找不到 → search 全量列表 → search 再试一次"的无效循环，浪费 token 和时间。
  • 严重T02 Confidence=low 但结果正确 — verdict 为 null（无历史缓存），导致置信度降级，但实际回答完全正确。置信度评估逻辑需要区分"无缓存"和"真正不确定"。
  • 设计groupBy=equipment 返回内部 ID 而非编号 — T11/T20 中 fault/anomaly 按 equipment 分组返回的是数字 ID（如"1666"、"1001"），AI 需要额外调 equipment.profile 才能拿到设备名称。MCP 应在聚合时解析为可读名称。
  • 设计数据脏值未清洗 — T04 设备状态分布中出现 group:"8"（1台），这是状态枚举的脏数据，不应原样输出给用户。
