Systemic Issues

1. The ID Resolution Problem (affects T29, T30, T33)

Three of six questions failed because fault.search and repair.search return groupBy results with numeric internal IDs that the AI cannot map to human-readable equipment names. The AI then wastes rounds trying to resolve these IDs via equipment.profile (which crashes) or equipment.search (which returns a massive list). Even when the ID lookup succeeds (T33), the AI cannot perform the in-context join.

Fix: All groupBy results must include the entity's name/code, not just its internal ID. Example: {"group": "1666", "groupName": "VMC-850 #1", "groupCode": "EQ001", "count": 6}.

2. The Silent Filter Failure Problem (affects T32)

When productionLine="A线" doesn't match a known line, the search tools return unfiltered data instead of an error. This gives the AI false confidence that it has line-specific data when it actually has global data. The AI never noticed the total (108) was identical to unfiltered queries.

Fix: If a filter parameter doesn't match any known entity, return {"warning": "productionLine 'A线' not found", "didYouMean": ["A产线", "生产线A"]}.

3. The In-Context Join Failure (affects T29, T33)

LLMs are fundamentally weak at performing set operations (intersection, difference) on lists of 18+ items with numeric identifiers. T33 is the clearest example: the AI had all the data and could not compute "18 fault IDs minus 3 maintenance IDs." This is not a prompt issue -- it is a capability limitation.

Fix: Consider a server-side cross-reference tool: eam.cross.analyze(setA={tool, field}, setB={tool, field}, operation="difference"). Or, at minimum, add a Prompt instruction that walks the AI through the set operation step-by-step.

4. The "Cannot Answer" vs. "Empty Result" Confusion (affects T34)

T34's AI had the answer (0 external repairs, so no overlap with key equipment) but reported "cannot determine." The AI conflated "no data returned" with "cannot answer the question." An empty result set IS an answer: "None."

Fix: Prompt instruction: "If one of your data sets is empty, the answer to 'which items overlap?' is 'none.' Report this as a finding, not as inability to answer."

5. Precision Metric is Misleading for L4

T34 gets precision=50% because it called equipment.search in addition to the expected repair.search. But equipment.search was the RIGHT call -- you need both sets to compute an intersection. T32 gets precision=25% because scope.overview failed and it had to call 3 fallback tools. The precision metric penalizes correct recovery behavior.

Fix: For L4 cross-domain questions, redefine expected tools to include ALL tools needed for the cross-domain analysis, not just the primary domain tools.

Conclusion

L4 routing is solved. L4 analysis is not.

All 6 questions achieved 100% tool recall. The domain coverage prompt successfully guides the AI to identify and fetch from multiple domains. This is a real achievement -- the routing layer handles cross-domain intent decomposition correctly.

But L4 is supposed to test cross-domain analysis, not just cross-domain fetching. Only T31 produced a genuine cross-referenced answer. T33 is the most damning case: perfect data collection, zero analysis. The AI collected 18 fault equipment IDs, 3 maintenance equipment IDs, and a full 165-device lookup table, then said "cannot determine."

The root causes split into two categories:
- MCP-level (fixable): groupBy returns opaque IDs, filters fail silently, Resolver crashes on numeric IDs, spare.search pagination bug.
- AI-level (harder): LLMs cannot reliably perform set operations on 18+ item lists with numeric identifiers. This is a known limitation that no amount of prompt engineering fully solves.
