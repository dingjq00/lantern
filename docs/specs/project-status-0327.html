3 步 think 架构

  • think 1 — 规划：5 步结构化思考，选择工具和参数
  • think 2 — 审查放开：Reflexion 式事实对比，检查返回数据是否覆盖用户意图
  • think 3 — finish：最终确认并生成回答

追查轮限制 1-2 轮，3 轮以上 AI 会重复调失败工具

5 步结构化模板

  • Step-Back：先理解意图不看工具，防关键词劫持

  • 验证：确认每个域都有工具覆盖
  • 输出：结构化 tool_calls

参数引用 {{N.path}}

  • 多层依赖一轮完成

Part 3 已确立的架构原则（8 条）

以下原则在 P1 调优过程中通过实验数据和架构迭代确立，不是理论猜测。后续调优遵循这些原则，不走回头路。

1

MCP 是动作，AI 是能力

MCP 工具负责"获取数据"（确定性执行），AI 负责"分析数据"（聚合/统计/推理）。聚合和统计不做成 MCP 工具。

来源：P1 调优实验 — 将统计类操作从工具中剥离后，准确率显著提升
2

Guide 是方法论，YAML 是具象化

guide/prompt 保持通用（零项目内容），YAML 工具描述是项目相关的具象化。换项目不改 guide，只换 YAML。

来源：查找表 guide（88%）vs 通用 guide（60%）— 28pp 差距是"作弊分"，用级联+模板补回
3

从错误中学习 > 记录正确答案

但信号必须来自外部，AI 自评是循环论证（同一个脑子犯的错自评也发现不了）。有效信号：用户反馈、工具返回值、Ground Truth。

来源：verdict（记 winner）60% 准确率下积累 40% 错误经验；AI 自评 lesson 已禁用
4

优化优先级：Prompt > AI 分析 > MCP 工具

Prompt 贡献 99%，模型升级仅 +0.6pp。mock 数据优化是片面的。优先投入 Prompt 优化。

来源：8 方案对比实验 — gpt-5.4-mini 94.2% vs gpt-5.4 94.8%
5

工具应同时接受业务编号和内部 ID（poka-yoke）

让工具难以被错误使用。例如 get_repair_detail 同时支持 orderCode 和内部 ID，get_equipment_detail 同时支持 equipmentCode 和内部 ID。

来源：架构原则 — 防呆设计，接真实 API 时落地
6

Summarize 绝对不能编造数据

数据不足时说"数据不足"，不猜测、不编造。宁可诚实地说不知道，也不给出错误答案。

来源：P1 规则层实现 — rules.md 底线约束
7

复杂度是输出不是输入 — 不预判

统一流程自然收敛复杂度。不对查询复杂度做预判，同一个流程处理 L1-L5 所有级别查询。

来源：P1 架构设计 — 分层/混合架构（90.5%/87.1%）不如扁平架构（94.2%）
8

静态上下文在前（可缓存），动态上下文在后

6 层 Context 架构的设计依据：Layer 1-4 静态可缓存，Layer 5-6 每次动态组装。Context Engineering 落地实践。

来源：Context Engineering 方法论 — 缓存边界优化 token 消耗

Part 5 P1.5 规划（下一阶段）

自学习重构 — 核心问题

自学习难的不是学习算法，是标注 — 怎么知道什么是对的什么是错的。
已验证失败的标注方式：verdict（记 winner）、AI 自评（循环论证）、thumbs up/down（用户不爱点）。

3 个解法对比

维度 解法 1: 高级模型蒸馏 解法 2: 多模型并行 解法 3: 工具返回值即信号 (首选)
原理 mini 执行后，5.4 异步评估 mini 的工具选择和回答 每个查询同时跑 2-3 个模型，用户选择即隐式标注 工具返回值本身就是验证信号 — 有数据+匹配=对，空/不匹配=错
成本 每次多一次 5.4 调用（可异步批量） 计算成本翻 2-3 倍 零成本，不需要额外模型调用
信号可靠性 5.4 有信息差，标注可靠 依赖用户判断力 客观事实（数据有没有），不依赖主观判断
天花板 受限于 5.4 能力上限 需要真实用户流量 无天花板限制
实现基础 需要新开发 需要新开发 + 前端改动 validator.ts 已有基础
优先级 P2 补充 P2 补充 P1.5 首选

首选方案：工具返回值即信号

来源：PlayCard 伙伴从第三方角度指出 — "不需要另一个模型来判断对错，工具返回值就是信号"。

  • 扩展 validator.ts，从"数值合理性检查"升级为"结果-问题匹配度检测"
  • 工具返回数据的字段 vs 用户问题的意图 → 是否匹配
  • 空结果检测："真没有" vs "选错工具"

  • 自学习循环：执行 → 结果非空且匹配 → 自动标为正确样本 / 结果空或不匹配 → 进人工审核

Part 7 经验教训（2026-03-26 全天调优总结）

以下经验来自 P0 → P1 编码 + benchmark 体系 + Prompt 调优的全天实战，每一条都有实验数据支撑。

1. 自由 CoT 对工具选择不够甚至有害

换成 5 步结构化模板（ToolGT）后效果显著提升。自由思考容易跑偏，结构化模板约束思考方向。Step-Back Prompting 先理解意图不看工具，防止关键词劫持。

2. Reflexion 式事实对比要问事实，不问判断

观察注入不问"够不够"（是非判断），问"有什么字段/缺什么"（事实陈述）。事实陈述让 AI 自己得出结论，比直接问是非判断更准确。

3. 级联策略贡献最大（+16pp）

mini 失败自动升级 5.4。但 Prompt 贡献 99%，模型升级仅 +0.6pp。先投入 Prompt 优化，级联是兜底。

4. 追查轮过多有害

3 轮追查时 AI 重复调失败工具，造成无效循环。1-2 轮追查就够了。三步 think 架构固定上限。

5. Ground Truth 本身要审查

8 题 GT 跳过了 ID 解析步骤，比 AI 还差。GT 修正后单次峰值从 87.5% 提升到 91.7%。评估体系的质量决定了调优的方向是否正确。

6. Verdict（记 winner）无效

60% 准确率下积累的是 40% 错误经验，越学越差。正确的积累，反而没有那么重要（dingjq 原话）。自学习的关键是外部信号，不是自我积累。

7. AI 自评（Lesson）无效 — 循环论证

同一个脑子犯的错，自评也发现不了。有效学习信号只有三种：用户反馈（thumbs down）、结果质量检测（空数据/字段不匹配）、Ground Truth（测试）。

8. 工具返回值即信号 — 最可靠的自学习方案

来自 PlayCard 伙伴的洞察：不需要另一个模型来判断对错，工具返回值就是信号。有数据+匹配实体=大概率对，空结果/不匹配=可能错。零成本，客观，这是 Context Engineering 的 feedback loop。

最终成果一句话

通用架构（零查找表）下 3 次平均 Recall 87.5%（GT 修正后峰值 91.7%）
组合：5 步模板 + 级联 + 参数引用 + 三步 think + 通用 guide + 6 层 Context 架构

核心认知：从"准确率调优"转向"自学习闭环"，信号来自外部不来自 AI 自己。
