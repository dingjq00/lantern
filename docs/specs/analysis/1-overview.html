Section 1: 架构全景 (Architecture Panorama)

1.1 四层架构总览

平台采用严格的四层分离架构，每层职责明确，单向依赖（上层 → 下层）。

接入层 Access Layer

Next.js API Routes -- 接收 HTTP 请求，初始化单例依赖，调用核心路由，返回 JSON 响应。

app/api/chat/route.ts · app/api/feedback/route.ts · app/api/benchmark/* · app/api/health/route.ts
智能层 Brain Layer

ReAct 循环编排 + LLM 推理 + 置信度融合 + 结果呈现 + 自学习评估。平台的核心大脑。

lib/brain/router.ts · prompt-assembler.ts · confidence.ts · intent.ts · result-presenter.ts · trace.ts · subagent-evaluator.ts · relevance-checker.ts · lib/llm/codex-proxy.ts
工具层 Tool Layer

Skill YAML 声明 + 工具注册表匹配 + MCP Client 通信 + MCP Server 12 工具执行 + Resolver 实体解析 + EAM API 调用。

lib/tools/registry.ts · yaml-loader.ts · mcp-client.ts · skills/eam/*.yaml(x12) · mcp-server/src/index.ts · handlers/*.ts(x12) · resolvers.ts · eam-api.ts
数据层 Data Layer

SQLite + WAL 三层记忆（会话/经验/偏好）+ 执行追踪 + 自学习 Lessons + Benchmark 追踪。

lib/storage/sqlite.ts · lib/storage/types.ts · lib/storage/migrations/*.sql

Section 2: 完整请求生命周期

2.1 "CNC-001 怎么样？" 完整 Walkthrough

以下逐步追踪一个真实查询从进入到返回的每一个函数调用、数据变换和决策分支。

API Route 接收请求
app/api/chat/route.ts :: POST()

Next.js API Route 收到 HTTP POST，解析 body：

// 请求体
{ "query": "CNC-001 怎么样？", "history": [] }

// 单例初始化（首次请求时）
getRegistry()  → loadTools('./skills') → new ToolRegistry(ToolDefinition[12])
getLLM()       → new CodexProxyProvider()
getStorage()   → new SQLiteStorage('./data/insight68.db')  + .initialize()
getMCPClient() → new MCPClient('npx', ['tsx', 'mcp-server/src/index.ts'])

调用 processQuery(query, deps) 进入智能层。

Router 初始化 -- ReAct 循环准备
lib/brain/router.ts :: processQuery()

创建 TraceCollector（生成 traceId t-xxxxxxxx），获取全部工具列表，初始化循环状态：

const trace = new TraceCollector("CNC-001 怎么样？")
const allTools = registry.getAllTools()  // 12 个 ToolDefinition
const MAX_CHASE_ROUNDS = 2  // 最多 3 次 think（round 0/1/2）
let round = 0, finished = false
Prompt 六层组装
lib/brain/prompt-assembler.ts :: assemblePrompt()

六层架构严格按序拼接。静态层在前（可缓存），动态层在后。

// Layer 1: system-prompt.md  → "你是 Insight68 企业智能助手..."
// Layer 2: rules.md          → 底线约束（不编造数据等）
// Layer 3: base-instructions.md + react-instructions.md + tool-selection-guide.md
// Layer 4: few-shot-examples.json → 格式化为编排示例
// --- 缓存边界 ---
// Layer 5: 动态上下文
//   系统: EAM | 数据域: equipment, fault-repair, ... | 工具数: 12 | 日期: 2026-03-28
//   可用工具（12 个工具的 name + description + params）
// [可选] 历史推荐路径（verdict 注入）
// [可选] 用户上下文（对话历史）

// Layer 6: 用户输入（在 messages 里，不在 system prompt 里）

返回 { systemPrompt: string, userMessage: "CNC-001 怎么样？" }

LLM Think -- 规划轮 (Round 0)
lib/llm/codex-proxy.ts :: think()

发送 messages 到 OpenAI 兼容接口（默认模型 gpt-5.4-mini，temperature=0），强制 JSON 输出：

// LLM 返回的 ThinkResult（Round 0 -- 规划轮）:
{
  "thought": "用户问 CNC-001 设备的状况，需要查设备全景画像",
  "intent": {
    "domains": ["equipment", "fault-repair", "maintenance"],
    "operation": "detail",
    "filters": ["equipmentCode"]
  },
  "clarity": "clear",
  "calls": [
    { "tool": "eam.equipment.profile", "arguments": { "identifier": "CNC-001" } }
  ],
  "finish": true
}

Zod schema (ThinkResultSchema) 验证输出格式。clarity: "clear" 经 mapClarity() 映射为 "high"。

意图提取 + Intent Hash 计算
lib/brain/intent.ts :: extractIntentFromThinkResult()

首轮（round===0）提取结构化意图：

// 输入: result.intent = { domains, operation, filters }
// 计算: SHA256( {"d":["equipment","fault-repair","maintenance"],"f":["equipmentCode"],"o":"detail"} )
//   → intentHash = "a3f7e2c1b9d04..." (前 16 位)

// 返回: { intent: IntentTags, clarity: 'high' }
// 用 intentHash 查 verdict: storage.getVerdict(tenantId, intentHash)
参数引用解析 + 工具执行
lib/brain/router.ts :: resolveArgRefs() + registry.execute()

遍历 thinkResult.calls，对每个 call 解析 {{N.path}} 引用（本例无引用），然后执行：

// 本例只有 1 个 call:
const call = { tool: "eam.equipment.profile", arguments: { identifier: "CNC-001" } }

// resolveArgRefs() -- 无 {{}} 引用，原样返回

// registry.execute() → 验证工具存在 → callTool()

结果回到 Router -- 观察注入
lib/brain/router.ts (循环体)

MCP Client 解析 JSON 返回 ToolResult { data, status: 'success' }，Router 记录 trace 并注入观察消息：

                status: "success", durationMs: 450 })
trace.endRound("已获得 1 个工具的结果")

// 观察注入到 messages（Reflexion 式事实对比）

  "观察结果: [{tool: 'eam.equipment.profile', result: {...}}]\n\n" +
  "事实对比:\n- 用户问: \"CNC-001 怎么样？\"\n- 已获得字段: equipment, kpi, recentFaults, ..."
})

由于 thinkResult.finish === true，循环结束。

置信度计算 -- 三信号融合
lib/brain/confidence.ts :: computeConfidence()
// 信号 1: toolMatch
//   totalCallsAttempted=1, allResults.length=1 → 全部成功 → "high"

// 信号 2: verdictConfidence
//   verdict = storage.getVerdict(tenantId, intentHash)
//   假设 sampleCount=15 → ≥10 → "high"（已有足够历史数据）
//   或 sampleCount=0 → <3 → "low"（新意图）

// 信号 3: queryClarity
//   LLM 返回 clarity="clear" → mapClarity() → "high"

// 融合规则:
//   3个 high → "high"
//   任1个 low → "low"
//   其余 → "medium"

// 本例（假设有历史数据）: signals = { high, high, high } → finalConfidence = "high"

级联升级分支（Mini 失败时）

如果 gpt-5.4-mini 首轮返回 unsupported: true 或无 calls，Router 自动级联到强模型：

// 级联策略 (router.ts L85-126)
if (thinkResult.unsupported || (!thinkResult.calls?.length && round === 0)) {
  const escalated = await llm.think(messages, 'gpt-5.4')  // ESCALATION_MODEL
  // 强模型也搞不定 → 生成上下文相关的"超纲"回复
  // 强模型给出 calls → 替换 thinkResult 继续执行
}

多轮追查分支

如果 LLM 认为数据不足（finish: false），进入追查轮（最多 2 轮追查）。观察结果注入 Reflexion 式事实对比，引导 AI 判断信息是否充足。

Section 5: 架构原则总结

5.1 MCP 固化层 vs Skill 进化层

分层设计哲学
MCP 工具（固化层）：确定性的数据获取逻辑。Resolver 模式、API 聚合、错误处理 -- 这些是稳定的，变化频率极低。一旦写好就像管道，数据进来、数据出去，不需要 AI 参与决策。

Skill YAML（进化层）：AI 路由决策的知识库。description、whenToUse/whenNotToUse、examples -- 这些是经常调优的，每次 Benchmark 回归后可能微调措辞。YAML 的修改不需要重启 MCP Server，热加载即可。

关键洞察：MCP 工具是"能力"，Skill YAML 是"认知"。能力稳定，认知进化。

5.2 Resolver 模式

公共标识符解析 -- Poka-yoke 防错设计
所有 MCP handler 通过 resolvers.ts 解析输入标识符。用户可以用名称、编号或 ID 任一形式，Resolver 统一处理：
exact match > startsWith > contains
唯一匹配返回实体，多个匹配返回候选列表（最多 5 个），由 AI 追问用户确认。

这个模式的价值：AI 不需要关心"用户给的是 ID 还是名称"，Resolver 兜底。

5.3 P1 确立的 8 条架构原则

原则 1: MCP 是动作，AI 是能力
MCP 负责获取数据（确定性），AI 负责分析数据（推理能力）。不混淆两者的职责边界。
原则 2: Guide/Prompt 是方法论，YAML 是具象化
Prompt 文件（rules.md, react-instructions.md 等）是通用方法论，YAML 是项目相关的具象化。保持 Prompt 层的通用性，方便扩展到其他企业系统。
原则 3: 从错误中学习 > 记录正确答案
Lesson 机制只在 quality !== 'good' 时记录。信号必须来自外部（subagent 独立评估或用户反馈），AI 自评无效。
原则 4: 优化优先级 -- Prompt > AI 分析 > MCP 工具
改 Prompt 措辞的 ROI 最高，改 MCP 工具是最后手段。大多数问题通过调整 description 或 whenToUse 就能解决。
原则 5: 工具同时接受业务编号和内部 ID（Poka-yoke）
通过 Resolver 模式实现。AI 不需要先查 ID 再查详情，一步到位。减少 LLM 调用轮次，降低出错概率。
原则 6: Summarize 绝对不能编造数据
LLM summarize prompt 中明确约束："只能基于提供的数据回答，绝对不能编造数据中没有的数字、百分比或结论。"宁可说"数据不足"。
原则 7: 复杂度是输出不是输入
不预判查询复杂度（简单/复杂）。统一流程（ReAct 循环）自然收敛：简单查询 1 轮完成，复杂查询自动追查。
原则 8: 静态上下文在前，动态上下文在后
Prompt 六层架构中，静态层（system prompt、rules、instructions）放在前面可缓存，动态层（工具列表、用户上下文）放在后面。利用 LLM 的 KV cache 优化。

5.4 关键设计决策速查

决策 选择 原因
路由方式 LLM ReAct 循环（不是 Text-to-SQL） 企业系统 API 已有，不需要裸查数据库；LLM 路由更灵活，可扩展到任何有 API 的系统
工具协议 MCP (Model Context Protocol) 标准协议，AI 生态兼容；stdio 隔离，MCP Server 独立进程；工具描述统一格式
LLM 级联 mini → 强模型（gpt-5.4-mini → gpt-5.4） 95%+ 查询 mini 就能搞定，只在超纲时升级，控制成本
存储引擎 SQLite + WAL 单机部署足够，零运维；WAL 模式支持并发读
Prompt 管理 文件系统（prompts/*.md + skills/*.yaml） 版本控制友好，diff 可读；不用数据库管 prompt
自学习信号源 Subagent 独立评估 + 用户反馈 AI 自评有偏见（generator-evaluator 问题）；subagent 隔离上下文消除偏见
置信度模型 三信号融合（toolMatch + verdict + clarity） 多维度交叉验证，避免单一信号误判
参数引用 {{N.path}} 语法 支持多步编排中的数据传递，AI 规划时声明引用关系，Router 运行时解析
