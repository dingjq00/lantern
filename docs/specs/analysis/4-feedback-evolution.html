1. Confidence Calculation -- 3-Signal Fusion

The confidence system is the platform's self-assessment of answer quality. It fuses three independent signals into a single high | medium | low level that drives both the user-facing response tone and internal evolution decisions.

1.1 The Three Signals

Signal 1 toolMatch

Did the tools actually execute successfully?

highAll attempted calls returned data (allResults.length === totalCallsAttempted)
mediumPartial success -- some calls succeeded, some failed
lowAll calls failed or zero calls attempted

Signal 2 verdictConfidence

Has the system seen this intent before?

highsampleCount >= 10 -- well-known query pattern
mediumsampleCount 3-9 -- some experience
lowsampleCount < 3 or no verdict exists

Signal 3 queryClarity

How clear was the user's intent? (LLM-assessed)

highLLM returned clarity: "clear"
mediumLLM returned clarity: "ambiguous"
lowLLM returned clarity: "unsupported"

1.2 Fusion Logic

// confidence.ts -- 27 lines, clean and deterministic
function computeConfidence(signals: ConfidenceSignals): ConfidenceLevel {
  const values = [signals.toolMatch, signals.verdictConfidence, signals.queryClarity]

  if (values.some(v => v === 'low'))  return 'low'    // 一票否决
  if (values.every(v => v === 'high')) return 'high'   // 全票通过
  return 'medium'                                      // 其余情况
}

The fusion is a pessimistic gate: any single low signal drags the entire confidence to low, while all three must be high for the result to be high. This is deliberately conservative -- better to show a caveat than to present garbage confidently.

1.3 Edge Case Analysis

ScenariotoolMatchverdictclarityResultFrequency
New system, first query ever, tools all succeed high low high low Very common at cold start
Repeat query with history, all tools pass high high high high Common after learning
Ambiguous query, tools partially succeed medium medium medium medium Common for L3-L5
Unsupported query, escalation also fails low low low low Out-of-scope
Well-known pattern, but tools error this time low high high low API flakiness
Key Observation: Cold Start Penalty
Until a query pattern accumulates 3+ sessions, verdictConfidence is always low, which forces the entire result to low regardless of perfect tool execution and clear intent. For a new deployment, every single response starts at low confidence until the verdict table builds up. This is correct for safety but pessimistic for user experience.

1.4 Signal Reliability with 12-Tool Design

SignalReliabilityAssessment
toolMatch Solid Directly measured from execution results. Objective ground truth. 12-tool design makes it even more reliable -- fewer tools means fewer failure modes.
verdictConfidence Fragile Depends on intentHash aggregation. With 12 tools, intent hashes may fragment less (fewer distinct routing paths), but the underlying problem remains: hash is computed from {domains, operation, filters} and slight wording variations produce different hashes for semantically identical queries.
queryClarity Soft LLM self-assessment of query clarity. Defaulting to 'high' when not returned means most queries get high clarity. The LLM has weak incentive to report ambiguity honestly -- it tends to try to answer everything.

1.5 How Confidence Affects User Response

The router passes finalConfidence into buildStructuredResult, which becomes part of StructuredResult. The frontend can:

  • high -- present answer directly, full confidence styling
  • medium -- present answer with caveat: "based on available data..."
  • low -- trigger clarification flow or show degraded response

Additionally, when the router detects unsupported from both mini and escalated model, it uses the LLM summarize() to generate a contextual unsupported message (not a hardcoded string), which is significantly better UX.

2. Result Presentation -- From Data to User Response

2.1 Display Format Detection

// result-presenter.ts -- detectDisplayFormat()
function detectDisplayFormat(data: unknown): DisplayFormat {
  if (Array.isArray(data))                    return 'multi_step'
  if (object with 'trend' or date series)    return 'timeseries'
  if (object with 'items' array)               return 'list'
  return 'single_value'
}
FormatData ShapeWhen Used
multi_stepArray (multiple tool results)L3/L4 cross-domain queries with multiple tool calls
timeseriesObject with trend or date arrayseam.trend results, monthly stats
listObject with items arraySearch results (equipment.search, fault.search)
single_valueEverything elseProfile lookups, dashboard stats, fallback
Architecture Insight
detectDisplayFormat is a hint passed to the LLM summarizer, not a hard UI decision. The LLM summarize() receives formatHint and returns its own display choice (text | table | chart). This creates a two-stage format decision: structural detection + LLM judgment. The LLM can override the structural hint based on the actual data content, which is the right design -- format should depend on semantics, not just data shape.

2.2 Summary Generation (LLM Summarize)

// codex-proxy.ts -- summarize() prompt (abridged)
"你是数据解读助手。根据查询结果生成简洁的中文回答。

严格规则：
- 只能基于提供的数据回答，绝对不能编造数据中没有的数字
- 宁可说"数据不足"也不能给出没有依据的数字
- 如果数据中有 unsupported 标记，基于 aiAnalysis 生成友好说明

followUp 规则（类似 Perplexity 的深入引导）：
- 3-5 个有价值的后续探索方向
- 祈使句写成可直接执行的指令"

Key quality controls in the summarizer:

  • Anti-hallucination rule: "Only based on provided data, never fabricate numbers" -- this is the most important rule for enterprise use cases where wrong numbers can cause real damage.
  • Graceful unsupported handling: When data contains unsupported marker, the summarizer generates a contextual explanation based on aiAnalysis from the escalated model's reasoning.
  • Follow-up generation: Perplexity-style imperative suggestions ("View equipment details for the most faulted device") that can be directly executed as new queries.

2.3 buildStructuredResult

// The final assembly -- pure data passthrough, no transformation
function buildStructuredResult(
  answer: string,               // LLM-generated natural language
  data: Record<string, unknown>[],  // Raw tool data
  display: string,              // table | text | chart
  confidence: ConfidenceLevel,   // high | medium | low
  columns?: string[],           // Table column hints
  followUp?: string[],          // Perplexity-style suggestions
): StructuredResult

This function is a pure assembler -- it attaches no behavior. The router adds sources, trace, and lessonEval after the call. This clean separation means the result object carries everything the frontend needs: answer + raw data + metadata + debugging info.

2.4 Sources Tracking

Sources are collected in the router during tool execution. Each successful tool call adds a { tool, description } entry, deduplicated by tool name. The trace.addSource() also deduplicates, but the router maintains its own sources array independently. This dual tracking is slightly redundant but harmless.

3. Trace & Session Storage -- The Audit Trail

3.1 TraceCollector Architecture

// trace.ts -- What gets captured in every query
ExecutionTrace {
  traceId:          "t-xxxxxxxx"          // UUID-based unique ID
  query:            "用户原始问题"
  startTime/endTime: number                // ms timestamps
  rounds: [                                  // ReAct loop records
    { round: 0, thought: "...",
      calls: [{ tool, arguments, result, status, durationMs }],
      observation: "..." }
  ]
  intent:           IntentTags              // domains, operation, filters, hash
  verdict:          MemoryVerdict | null    // historical verdict if exists
  confidence:       ConfidenceSignals       // 3-signal breakdown
  finalConfidence:  ConfidenceLevel         // fused result
  validation:       ValidationResult[]      // (currently unused)
  sources:          Array<{tool, description}>
}
Trace Completeness Assessment
The trace captures everything needed for debugging: the full reasoning chain (thought per round), every tool call with arguments and results, timing data, intent extraction, verdict state, and confidence breakdown. This is excellent infrastructure -- you can replay any query's execution path from the trace alone. The validation array exists in the type but is never populated in the current router code (no validators are invoked). This is a hook for future use.

3.3 Session Data -- What's Stored

// Written in router.ts after every successful query
MemorySession {
  sessionId:        traceId,                // Reuses trace ID as session ID
  userId, tenantId, query,
  intentHash:       intent?.intentHash ?? '',
  toolChain:        allResults.map(r => r.tool),
  resultSummary:    answer.slice(0, 200),   // Truncated!
  routingDecision:  { rounds, confidence },
  expiresAt:        now + 30 days           // 30-day retention
}
Data Retention Design
Sessions expire after 30 days (set at creation, not enforced by cleanup). There is no cleanup job that actually deletes expired sessions. The expiresAt field is written but never checked by any query. The verdict system also sets 30-day expiry, also never enforced. For a production system, this means data grows unbounded.

3.4 Trace Storage Pattern

Traces are stored as a monolithic JSON blob in trace_json TEXT. This makes them trivially easy to store and retrieve but impossible to query at the SQL level. You can't ask "show me all traces where eam.fault.search took more than 2 seconds" without parsing every JSON blob.

For the current scale (single-tenant, tens of queries per day), this is fine. At scale, this would need either: (a) extract key metrics to indexed columns, or (b) use a JSON-aware database.

3.5 Benchmark Storage

Benchmark runs store the full config + summary + per-question results as JSON blobs. The getBenchmarkRuns() method returns summaries for the Dashboard, and getBenchmarkRun(runId) retrieves full detail for drill-down. This enables historical comparison ("did recall improve after this prompt change?") and is the best implementation of experiment tracking in the codebase.

4.2 The Evaluator Prompt

"你是结果质量评估员。你不知道 AI 是怎么选工具的，也不需要知道。
你只需要判断：给定的数据能回答用户的问题吗？

规则：
- 只看数据和问题，不要猜测或推理
- 数据字段和问题主题明显不匹配 → bad
- 数据有部分相关但不够完整 → partial
- 数据足以回答问题 → good"

This is the Anthropic generator + evaluator pattern: the evaluator is deliberately isolated from the generator's reasoning. It can't see why tools were chosen, only what data came back. This eliminates the circular self-evaluation problem ("I chose well because I chose well").

4.3 Quality Assessment Output

QualityMeaningAction
good Data is sufficient to answer the question No lesson written. Positive signal for verdict.
partial Data is partially relevant but incomplete Lesson written with [subagent] prefix. Missing fields logged.
bad Data doesn't match the question at all Lesson written. Strong negative signal for verdict.

4.4 Lesson Generation and Storage

// Written in router.ts after subagent evaluation
if (subagentResult.quality !== 'good' && intent?.intentHash) {
  storage.insertLesson({
    intentHash, tenantId, query,
    selectedTools: allResults.map(r => r.tool),
    quality: subagentResult.quality,
    errorReason: subagentResult.reason,
    betterPath: subagentResult.missing,          // What's needed
    lesson: `[subagent] ${subagentResult.lesson}`,
    source: 'self_eval',                       // Marked as AI-generated
  })
}

Lesson storage uses upsert-by-source semantics: for the same (tenant_id, intent_hash, source), only the latest lesson is kept. This prevents lesson accumulation from repeated queries.

4.5 Historical Context: The 78 Deleted Lessons

Previous Experiment Failure

During P1 self-learning experiments, the subagent evaluator (then with a different, less isolated prompt) produced 78 lessons that were all garbage -- vague, repetitive, and unhelpful. They were manually bulk-deleted. The root cause was that the original evaluator had access to the routing reasoning, making it a circular self-evaluation (AI evaluating its own reasoning is like a student grading their own exam).

The current isolated subagent design addresses this by cutting off access to the routing context. However, the source: 'self_eval' tag means these lessons are still distinguishable from human feedback, allowing different trust levels.

4.6 Current Status: Still Running?

Yes, the subagent evaluator runs on every query. Looking at router.ts, the evaluation block runs unconditionally after every successful query (lines 239-261). There is no confidence gate or cost optimization -- every query pays for an extra LLM call for evaluation. The earlier design doc proposed "confidence high → skip evaluator" but this was not implemented.

4.7 Integration with Skill Evolution Vision

Lessons from the subagent are stored with selectedTools and betterPath (missing info). In the Skill evolution vision, these would be aggregated to identify which Skills consistently produce partial or bad results and what data they're missing, then fed to a higher-level AI to propose YAML modifications. Currently, this aggregation and YAML modification is entirely manual.

5.4 intentHash Fragmentation Issue

// intent.ts -- How the hash is computed
function computeIntentHash(domains, operation, filters) {
  const normalized = {
    d: [...domains].sort(),
    o: operation,
    f: [...filters].sort(),
  }
  return sha256(JSON.stringify(normalized)).slice(0, 16)
}
Fragmentation Problem

Two queries that are semantically identical but phrased differently will produce different intent hashes if the LLM extracts different filters or operation values:

  • "Show me equipment EQ-001 details" → {d:["equipment"], o:"detail", f:["EQ-001"]}
  • "What's the info for device EQ-001?" → {d:["equipment"], o:"query", f:["EQ-001"]}

Different operation → different hash → different verdict entry → learning never aggregates. With 12 tools this is somewhat mitigated (fewer routing paths), but the fundamental problem remains: verdict learning is only as good as intent hash stability.

5.5 Verdict System -- Current Value Assessment

The verdict system (verdict.ts) aggregates session data into a per-intent-hash scoring:

  • User feedback weighted 3x (thumbs up = 1.0 * 3, thumbs down = 0.0 * 3)
  • No feedback = neutral (0.5 * 1 weight)
  • Lesson quality deduction (bad = -0.5, partial = -0.2)
  • Winner chain = most frequent tool chain across sessions

The verdict is injected into the prompt as "historical recommended path" by the prompt-assembler, giving the LLM a hint about what worked before. It also contributes to verdictConfidence, the second confidence signal.

Verdict Effectiveness Assessment

In theory, verdicts should improve routing accuracy for repeated query patterns. In practice:

  • Without user feedback, most sessions have feedback: null, scoring 0.5 with weight 1 -- essentially noise
  • Subagent lessons deduct from score, but their quality was previously proven unreliable
  • The hash fragmentation issue means verdicts rarely aggregate enough samples
  • The prompt injection is a soft hint ("historical path") that the LLM may or may not follow

Net assessment: The verdict system is architecturally sound but has weak input signals. It's infrastructure waiting for better data (user feedback, stable hashes).

6.2 acceptablePaths -- Multiple Valid Routes

Each test case defines acceptablePaths: string[][] -- a list of valid tool sequences. This is a critical design decision: there is no single "correct" answer, only multiple acceptable paths. For example, T06 "Patrol anomaly stats" accepts three paths: 

acceptablePaths: [
  ['eam.dashboard'],          // Dashboard has anomaly stats
  ['eam.anomaly.search'],      // Direct anomaly search
  ['eam.patrol.search'],       // Patrol search also has anomaly data
]

6.3 Scoring: calcBestMatch Algorithm

function calcBestMatch(actual: string[], acceptablePaths: string[][]) {
  // For each acceptable path, compute recall and precision
  // Return the path that gives the highest recall (ties broken by precision)

  for (const expected of acceptablePaths) {
    recall    = |expected ∩ actual| / |expected|   // Did we hit the expected tools?
    precision = |expected ∩ actual| / |actual|     // Were our calls relevant?
  }
  // Best match = highest recall, then highest precision
}

Key properties:

  • Recall: "Did we call the tools we should have called?" -- 100% means all expected tools were called
  • Precision: "Were all our calls useful?" -- 100% means no wasted calls
  • Multiple paths: A query that routes to any acceptable path scores well
  • Set-based: Order doesn't matter, only which tools were called

6.5 The 3 Remaining Failures -- Root Cause Analysis

Based on the test case definitions and the system's routing patterns, the most likely failure categories are:

L4/L5 Multi-Tool Chains -- Second Tool Not Called

For queries like T29 "Highest fault rate device -- is maintenance on track?" that require eam.fault.search + eam.maintenance.search, the LLM may stop after the first tool and attempt to answer from partial data. The ReAct loop should trigger a chase round but the LLM's "finish" signal fires too early.

Root cause: The observation injection shows fields from the first call, and the LLM decides "this is enough" without realizing the question has two parts.

Fix direction: Strengthen the Reflexion prompt in the observation message. Currently it says "if covered then finish" -- could add "check if ALL parts of the question are covered".

L5 Trend + Cross-Domain -- Composite Skill Gap

Questions like T35 "Which line has rising faults AND low spare stock?" require combining eam.trend with eam.spare.search. With 1:1 Skill mapping, the LLM must independently decide to call both. When these become composite Skills with explicit tool lists, the LLM won't need to figure out the combination itself.

Fix direction: Create composite Skills for common cross-domain patterns. This is exactly the Skill evolution vision.

Ambiguous Domain Mapping -- Dashboard vs Search

Several L1 queries accept both eam.dashboard and domain-specific search as valid paths. The LLM may choose the "wrong" one for the benchmark even though both would answer the question. This is more a benchmark design question than a routing failure.

Note: The acceptablePaths design already handles this by allowing multiple valid routes. Any remaining "failures" in this category would indicate the LLM chose a path not in the acceptable set at all.

6.6 Benchmark as Evolution Driver

The benchmark is currently the strongest feedback signal in the entire system. It provides:

  • Objective measurement: recall/precision against expert-defined ground truth
  • Per-level breakdown: shows exactly where complexity starts causing failures
  • Historical tracking: runs stored in SQLite, Dashboard shows trends
  • Reproducible: same 40 questions, deterministic scoring

In the evolution loop, benchmark is the validation gate: any Skill YAML change must pass the benchmark before deployment. This is the equivalent of a test suite for AI behavior.

8. Issues & Recommendations

P0 Verdict Never Triggered -- Experience Layer is Dead Code

File: lib/brain/router.ts / lib/brain/verdict.ts

maybeUpdateVerdict() is never called. Sessions are written, verdicts are checked, but the bridge between them -- recalculating the verdict from accumulated sessions -- doesn't exist in the running code. The entire verdict aggregation system (scoring, winner chain, confidence, bonus points) is exercised only in tests.

Fix: Add maybeUpdateVerdict(storage, tenantId, intent.intentHash) after storage.insertSession() in router.ts. One line, high impact.

P0 Subagent Evaluator Runs Unconditionally -- Cost Waste

File: lib/brain/router.ts lines 239-261

Every query pays for an extra LLM call to evaluate itself. The design doc specified a confidence gate (skip evaluation when confidence is high), but this was never implemented. At scale, this doubles LLM costs for queries that are clearly correct.

Fix: Add if (finalConfidence !== 'high') { ... evaluate ... } guard. But note: until verdictConfidence is fixed (P0 above), confidence is never 'high', so the gate won't help until the verdict system is live.

P1 intentHash Fragmentation -- Learning Doesn't Aggregate

File: lib/brain/intent.ts

The hash over {domains, operation, filters} is too sensitive to LLM output variation. "What's device EQ-001's status?" and "Show me equipment EQ-001 details" may produce different operations ("query" vs "detail") and thus different hashes.

Options:

  • (a) Normalize operation to a smaller set (query/detail/list/trend/alert) with explicit mapping
  • (b) Use the actual tool chain as the aggregation key instead of intent hash
  • (c) Add fuzzy matching: if two hashes resolve to the same tool chain, merge their verdicts
P1 Lessons Written but Never Read During Routing

File: lib/brain/router.ts / lib/brain/prompt-assembler.ts

Lessons are written to nl_lessons on every non-good evaluation, but they're only read by the verdict scoring function (as a negative signal). They're never injected into the routing prompt as "avoid this pattern" hints. The prompt-assembler has no lesson injection.

Fix: Either inject top lessons into the prompt (risky -- proven to produce garbage before) or use lessons only for verdict scoring + Skill YAML evolution (safer).

P1 No Data Retention Enforcement

File: lib/storage/sqlite.ts

expiresAt is set on sessions and verdicts (30-day TTL) but no cleanup job exists. Traces and lessons have no expiry at all. Data grows unbounded.

Fix: Add a periodic cleanup: DELETE FROM nl_memory_sessions WHERE expires_at < datetime('now'). For traces, consider archiving old traces to file before deletion.

P2 Cold Start Confidence Penalty

File: lib/brain/confidence.ts

New deployments always show low confidence because verdictConfidence starts at low. This is technically correct but creates a poor first impression.

Options:

  • (a) Pre-seed verdicts from benchmark results (37/40 known-good paths)
  • (b) Weight verdictConfidence less in the fusion (don't let one signal veto)
  • (c) Use 2-of-3 voting instead of pessimistic gate for first N queries
P2 Trace Storage Not Queryable

File: lib/storage/migrations/002-trace.sql

Traces stored as monolithic JSON in trace_json TEXT. Cannot query "show me all traces where a specific tool failed" or "average latency for eam.fault.search" without parsing every record.

Fix: Extract key metrics (total_duration_ms, tool_count, has_error, final_confidence) into indexed columns. Keep the full JSON for detail views.

P2 displayFormat Detection Misses Common Patterns

File: lib/brain/result-presenter.ts

detectDisplayFormat checks for trend, date series, and items array, but many EAM API responses don't follow these patterns. Equipment profile returns a flat object (→ single_value), search results may return records instead of items, etc. The detection is fragile against API response shape variation.

Mitigated by: The LLM summarizer can override the format hint, so this is a soft problem. But tighter detection would produce better default suggestions.

P3 Dual Source Tracking (Router + TraceCollector)

File: lib/brain/router.ts

The router maintains its own sources array AND the TraceCollector has addSource(). Both deduplicate independently. This is harmless but slightly confusing. The router's sources end up on the result; the trace's sources end up in the trace JSON. They should always be identical.

Fix: Use only TraceCollector's sources and copy them to the result at the end.
