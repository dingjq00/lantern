1.2 MAX_CHASE_ROUNDS = 2: Analysis

Design Intent The constant name is MAX_CHASE_ROUNDS = 2, but the loop condition is round <= MAX_CHASE_ROUNDS, which means up to 3 iterations (round 0, 1, 2). The comment says "1. Plan -> 2. Review + expand -> 3. Finish, max 3 think calls."
RoundPurposeTypical Behavior
0Initial planningLLM reads system prompt + query, produces tool calls. Extract intent. Most simple queries finish here (finish=true on same round).
1Review + chaseAfter seeing Round 0 results, LLM decides if more data needed. Can issue additional calls or finish.
2Final chanceIf Round 1 still needs more, one more round. If still not finished, the loop exits silently.

What happens at the boundary?

Silent Termination at Round 2 When round exceeds MAX_CHASE_ROUNDS, the while loop exits silently. There is no explicit "timeout" or "max rounds reached" signal. The code proceeds directly to confidence computation and summarization with whatever data has been gathered so far. This means:
  • If the LLM keeps requesting more tools at Round 2 without setting finish=true, those calls ARE executed (because the check is at the top of the loop), but the observation is injected without a subsequent think() call.
  • No trace entry records "max rounds reached" -- the trace simply shows the rounds that completed.
  • The LLM's final summarize() still gets all accumulated data, so the user gets a response, but it may be incomplete.

Is 3 iterations enough?

For the current 12-tool EAM scenario, 3 iterations is sufficient for virtually all queries:

  • Simple queries (80%+): Finish in Round 0 -- single tool call, immediate finish.
  • Two-step queries (15%): Round 0 gets equipment profile, Round 1 chases fault details. Finish at Round 1.
  • Cross-domain queries (5%): Round 0 gets overview data, Round 1 chases specifics, Round 2 resolves final detail. This is the theoretical max for 12 tools.

Risk scenario: A future expansion to 30+ tools with deeper dependency chains (e.g., equipment -> fault -> repair -> spare -> supplier) could exceed 3 rounds. Recommendation: add a configurable per-query maxRounds or make the constant tenant-configurable.

1.4 {{N.path}} Parameter Reference

The resolveArgRefs() function enables tool chaining by resolving {{N.path}} references in arguments, where N is the 0-based index of a previous call result within the same round.

// Example: Call 0 returns {items: [{equipmentId: 42}]}
// Call 1 references: identifier: "{{0.items[0].equipmentId}}"
// Resolved to: identifier: 42

function resolveArgRefs(args, results) {
  for (const [key, value] of Object.entries(args)) {
    if (typeof value === 'string' && value.startsWith('{{') && value.endsWith('}}')) {
      resolved[key] = navigatePath(ref, results)
    } else if (typeof value === 'object') {
      resolved[key] = resolveArgRefs(value, results)  // recursive for nested
    }
  }
}
FeatureStatusNotes
Simple path: {{0.id}}WorkingDot-separated navigation
Array index: {{0.items[0].equipmentId}}WorkingRegex match on /^(\w+)\[(\d+)\]$/
Nested objects in argsWorkingRecursive resolveArgRefs for nested arg objects
Array argsNot HandledArrays in args are passed through (not resolved). If LLM sends ["{{0.id}}"], it won't be resolved.
Cross-round referencesN/AroundResults is per-round only. Cross-round must go through LLM re-reasoning.
Failure fallbackGracefulReturns original ref string on failure + console.warn
Warning log coverageComplete4 distinct console.warn paths: index out of range, path interrupted, final value null, exception
Limitation: Only within same round References only work within a single round's calls (roundResults). If Call 0 is in Round 0 and the LLM wants to reference it in Round 1, it must extract the value from the observation message and pass it as a literal argument. This is by design (keeps the system simple), but worth documenting for future tool authors.

1.5 Message Context Management

After each round of tool execution, two messages are injected into the conversation:

// 1. Assistant message: the LLM's think result (including calls)
messages.push({ role: 'assistant', content: JSON.stringify(thinkResult) })

// 2. User message: observation + Reflexion-style fact comparison
messages.push({ role: 'user', content:
  `观察结果: ${JSON.stringify(obsData)}\n\n` +
  `事实对比:\n- 用户问: "${query}"\n` +
  `- 已获得字段: ${dataFields.join(', ')}\n\n` +
  `按 5 步模板继续推理。如果已覆盖用户问题则 finish。`
})
Design ChoiceRationaleImpact
Full JSON of thinkResult as assistant msgMaintains chain-of-thought visibility for subsequent roundsCan be large -- includes thought + calls + intent
obsData uses roundResults (not allResults)Avoids confusion from accumulated cross-round dataClean separation per round
Data field extraction for fact comparisonReflexion pattern -- helps LLM assess coverageEffective for determining "do I have enough?"
"按 5 步模板继续推理"Anchors LLM to structured output formatReduces format drift across rounds
Potential Issue: Message Context Growth Each round adds 2 messages with full tool results serialized as JSON. For tools returning large datasets (e.g., equipment search with 50 items, or trend with 500 records), the context can grow quickly. With 3 rounds of data-heavy calls, token usage could spike significantly. Consider truncating tool results in the observation message while keeping full data for summarization.

2.4 Data Serialization

The entire data pipeline uses JSON-as-text through MCP's text content type:

// Handler side: serialize to JSON text
return { content: [{ type: 'text', text: JSON.stringify(data, null, 2) }] }

// Client side: parse back to object
const data = JSON.parse(textContent.text)
return { data, status: 'success' }

// Fallback: if parse fails, return raw text
return { data: textContent.text, status: 'partial' }
Performance Note JSON.stringify(data, null, 2) in every handler uses pretty-printing (2-space indent). For large datasets this adds ~30% size overhead over compact JSON. Since this goes over stdio pipe and is immediately re-parsed on the client side, consider using JSON.stringify(data) without indentation in production.

2.5 Concurrency Model

// Router: calls within a round are SEQUENTIAL (for {{N.path}} references)
for (let ci = 0; ci < thinkResult.calls.length; ci++) {
  const call = thinkResult.calls[ci]
  const resolvedArgs = resolveArgRefs(call.arguments, roundResults)
  toolResult = await registry.execute(call.tool, resolvedArgs, callTool)
  roundResults.push(toolResult.data)  // available for next call's {{ci.path}}
}
Sequential-by-design Trade-off All calls in a round run sequentially because call N+1 may reference call N's result via {{N.path}}. This is correct for correctness, but if the LLM issues 3 independent calls (no references between them), they could theoretically run in parallel. An optimization would be to analyze the dependency graph of references and parallelize independent calls.

S3 Resolver Deep Dive

The resolvers.ts module provides the critical identifier-to-entity resolution layer. All profile and search handlers depend on it to accept human-friendly identifiers (names, codes) rather than just database IDs.

3.1 resolveEquipment: Matching Strategy

resolveEquipment(identifier) | +-- Pure digits (/^\d+$/)? | +-- YES: eamGet('/eam/equipment/get', {id}) | | +-- found -> match: 'exact' | | +-- error -> match: 'none' | +-- NO: continue | +-- eamGet('/eam/equipment/page', {keyword, pageNo:1, pageSize:10}) | +-- 0 results? -> match: 'none' | +-- Exact match (code === id OR name === id)? -> match: 'exact' | +-- startsWith match (single)? -> match: 'exact' | +-- Only 1 result total? -> match: 'exact' | +-- Multiple? -> match: 'candidates' (top 5)

5.4 Rate Limiting & Concurrency

No Rate Limiting Controls The EAM API client has zero rate limiting or concurrency controls:
  • No request queue or semaphore
  • No retry with backoff on 429 responses
  • No concurrent request limit
  • eamParallel uses Promise.allSettled which fires all calls simultaneously
The equipment-profile handler fires 7 parallel calls; dashboard fires 8. Combined with repair-search's per-item enrichment (up to 20 calls), a single user query could generate 30+ simultaneous API calls. If the EAM backend has rate limits, this will fail.

S6 Issues & Recommendations

All findings consolidated with severity and actionable recommendations.

6.1 Critical Issues

CRITICAL
I-01: LLM API errors not caught in router
llm.think(messages) and llm.summarize() are called without try-catch in the main flow. A network timeout, API error, or rate limit from the LLM provider will crash the request with an unhandled exception, returning a 500 to the user.
File: lib/brain/router.ts lines 70, 90, 217
Fix: Wrap LLM calls in try-catch. On think() failure, return a graceful "service temporarily unavailable" response. On summarize() failure, return raw data with a note.
CRITICAL
I-02: scope-overview fetches global data and filters in memory
The handler pulls pageSize=200 for faults, repairs, maintenance, and anomalies without any scope filter, then filters by equipmentId in JavaScript. This means: (a) data beyond page 1 is lost, (b) counts are wrong when total > 200, (c) unnecessary data transfer.
File: mcp-server/src/handlers/scope-overview.ts lines 75-91
Fix: Use equipmentId API filters where available. For domains without server-side equipment filter, iterate equipment IDs and aggregate.

6.2 High Severity Issues

HIGH
I-03: HTTP status codes not checked in eam-api
eamGet and eamPost call res.json() without checking res.ok. A 500 response might not parse as JSON (e.g., HTML error page), causing a cryptic JSON parse error instead of a clear API error.
File: mcp-server/src/eam-api.ts lines 52-63, 70-84
Fix: Add if (!res.ok) throw new Error(`HTTP ${res.status}`) before JSON parsing.
HIGH
I-04: No request timeout on EAM API calls
Neither the MCP client nor the EAM API client has a timeout. A hung EAM backend will block the entire request chain indefinitely.
File: mcp-server/src/eam-api.ts, lib/tools/mcp-client.ts
Fix: Add AbortSignal.timeout(30000) to fetch calls. Add a timeout wrapper on MCPClient.callTool().
HIGH
I-05: eam.trend splitBy parameter declared but not implemented
The splitBy parameter is in the schema (users can request it, LLM can generate it) but the handler body never uses it. Silently ignored -- users get unsplit data when they asked for split-by-equipment comparison.
File: mcp-server/src/handlers/trend.ts line 17
Fix: Implement splitBy logic or remove the parameter from the schema until implemented.
HIGH
I-06: Message context growth unbounded
Each round injects full tool results (JSON-serialized) into the message history. Large results (equipment lists, trend data with hundreds of records) inflate context rapidly. A 3-round query with data-heavy tools could easily push 50K+ tokens.
File: lib/brain/router.ts lines 180-193
Fix: Truncate observation data in messages (e.g., first 3 items + total count). Keep full data in allResults for final summarization.

6.3 Medium Severity Issues

MEDIUM
I-07: getEquipmentIdsByDepartment hard-coded pageSize=1000
Silently drops equipment beyond 1000 per department. No warning log.
File: mcp-server/src/resolvers.ts line 128
Fix: Add if (page.total > 1000) console.warn(...) and consider pagination.
MEDIUM
I-08: Concurrent token renewal race condition
Two parallel API calls finding expired token both trigger login. Wasteful but not breaking.
File: mcp-server/src/eam-api.ts lines 12-37
Fix: Singleton promise guard (see Section 5.1).
MEDIUM
I-09: Array arguments not resolved for {{N.path}} references
resolveArgRefs handles strings and nested objects but not arrays. If LLM sends ["{{0.id}}"] as an argument, the reference won't be resolved.
File: lib/brain/router.ts lines 282-295
Fix: Add array handling: if (Array.isArray(value)) resolved[key] = value.map(...)
MEDIUM
I-10: STATUS_MAP duplicated across 3+ files
equipment-profile, equipment-search, and scope-overview all define identical STATUS_MAP and REPAIR_STATUS constants.
Files: Multiple handler files
Fix: Extract to a shared constants.ts module.
MEDIUM
I-11: maintenance-search overdue silently overrides status
If both status and overdue=true are provided, overdue wins without warning. LLM might send conflicting parameters.
File: mcp-server/src/handlers/maintenance-search.ts lines 39-40
Fix: Check for conflict: if (args.status !== undefined && args.overdue) console.warn(...)
MEDIUM
I-12: trend handler pageSize=500 cap
For long date ranges, 500 records may not cover the full period. Trend data will be incomplete with no warning to the user.
File: mcp-server/src/handlers/trend.ts line 69
Fix: Add total-vs-fetched comparison in response: { totalInRange: page.total, fetched: records.length, warning: page.total > 500 ? 'Data truncated' : null }
MEDIUM
I-13: No user/person name resolution
responsiblePersonIds, assigneeId, and other person references are returned as raw IDs. The LLM has to present these as numbers, which is poor UX.
Files: equipment-profile, repair-profile, maintenance-search
Fix: Add a resolveUserNames(ids: number[]) utility that batch-fetches user names from /system/user/get.
