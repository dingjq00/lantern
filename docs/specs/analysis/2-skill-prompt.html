1 6-Layer Context Architecture

The prompt is assembled by lib/brain/prompt-assembler.ts in a strict 6-layer order. The design principle: static content first (cacheable), dynamic content last. This section dissects each layer.

Layer 1
System Prompt
File: prompts/system-prompt.md STATIC
Content: "你是 Insight68 NL-API 平台的 AI 助手，帮助制造业用户用自然语言查询和分析企业系统数据。"
Purpose: Identity anchor. Constrains AI persona to the platform context. Single sentence -- intentionally minimal.
Issues: None. Correctly minimal and system-agnostic. Could mention EAM but deliberately doesn't (allows multi-system extension).
Layer 2
Rules
File: prompts/rules.md STATIC
Content: 5 hard rules: no data fabrication, honest uncertainty, only listed tools, JSON-only output, business ID support.
Purpose: Guardrails. Placed early for maximum attention weight in transformer architecture.
Issues: MEDIUM Rule 4 "只返回 JSON" conflicts with the ReAct instructions which allow finish: true and thought reasoning. The intent is that the LLM should return structured JSON rather than prose, but the phrasing is ambiguous -- a strict reading would forbid the thought field's natural language content. LOW Rule 5 "参数支持业务编号" is a design principle, not a behavioral rule for the AI. Could be moved to task instructions.
Layer 3
Task Instructions
Files: prompts/base-instructions.md + prompts/react-instructions.md + prompts/tool-selection-guide.md STATIC
Content: 3 files concatenated: base rules (5 points), ReAct 5-step thinking template, tool selection method (6 sections with tables).
Purpose: The "how to do the job" layer. Most complex layer. Defines the reasoning framework, output format, and tool selection heuristics.
Issues: CRITICAL Operation type mismatch between tool-selection-guide.md and actual YAML files. The guide references detail / search / statistics / dashboard / trend, but types.ts defines ToolOperation = 'list' | 'detail' | 'statistics' | 'trend' | 'alert' | 'mutation'. The YAMLs use search (6 files) and dashboard (1 file) which are NOT in the TypeScript union type. See Section 3 for full analysis.
MEDIUM Redundancy: base-instructions and react-instructions both say "传名称不传 ID" and "一个工具能搞定就不要拆成多个". The duplication wastes ~200 tokens but does reinforce the message.
Layer 4
Examples
File: prompts/few-shot-examples.json STATIC
Content: 6 few-shot examples covering: dashboard, profile, repair.profile, cross-domain (fault+maintenance), scope.overview, trend+spare.
Purpose: Demonstrate correct tool selection and the 5-step thought template in action.
Issues: MEDIUM Coverage gaps: No example shows patrol.search, anomaly.search, or equipment.search. These 3 tools have zero few-shot representation.
LOW Example 3 uses "WO-201" as a repair order identifier, but the repair.profile description says the format should be "RO..." for repair orders. Minor inconsistency that won't break resolution but sets a bad example.
Layer 5
Dynamic Context
Assembled at runtime by: prompt-assembler.ts lines 92-129 DYNAMIC
Content: Current environment (systems, domains, tool count, date), full tool descriptions (name + description + parameter list), optional verdict injection, optional user memory context.
Purpose: Everything that changes per request or per tool config update. Placed after the cache boundary separator.
Issues: MEDIUM Tool descriptions are generated from inputSchema.properties only -- the when_to_use / when_not_to_use fields from YAML are loaded by yaml-loader but never injected into the prompt. These rich routing hints exist in the YAML but are invisible to the LLM.
MEDIUM The examples field from each YAML skill is also never injected into the prompt. The per-tool examples in YAML are dead data from the LLM's perspective.
LOW The generated tool description format is plain text. Anthropic's best practices recommend structured tool descriptions with explicit parameter schemas for tool_use, not inlined text blocks.
Layer 6
User Input
Source: The user's query, passed as userMessage (separate from systemPrompt) DYNAMIC
Content: Raw natural language query from the user.
Purpose: Kept separate as the user message in the API call, not concatenated into system prompt. This is correct per Anthropic best practices.
Issues: None. Clean separation.

Cache Boundary Analysis

The assembler inserts a --- separator between Layer 4 (examples) and Layer 5 (dynamic context). Layers 1-4 are loaded once and cached in module-level variables via lazy initialization. Layer 5-6 are assembled fresh per request.

Token budget estimate:

LayerEst. TokensCache StatusNotes
1. System Prompt~30STATICSingle sentence
2. Rules~100STATIC5 short rules
3. Task Instructions~1,200STATIC3 files, heaviest static layer
4. Examples~1,500STATIC6 JSON examples with thoughts
5. Dynamic Context~2,000DYNAMIC12 tool descriptions + env + verdict
6. User Input~20-100DYNAMICVaries per query
Total~4,850-4,930~60% static, ~40% dynamic

Anthropic Prompt Caching Opportunity: Layers 1-4 (~2,830 tokens) could use Anthropic's prompt caching feature to reduce costs by ~90% on cache hits. The cache boundary is already architecturally clean. However, the current implementation does NOT use Anthropic's API-level prompt caching -- it only caches the text in memory (avoiding file I/O), not at the API billing level.

3 matchScore Algorithm Analysis

Algorithm Breakdown

matchScore = domain(40) + operation(30) + filter(20 x coverage%) + chain(10)

domain(40):     intent.domains has ANY overlap with tool.domains  --> +40
operation(30):  tool.operation === intent.operation                --> +30
filter(20):     (matched filters / total intent filters) * 20     --> 0..20
chain(10):      tool.feedsInto.length > 0 || tool.dependsOn.length > 0  --> +10

Critical Issue: Operation Type Mismatch

TypeScript ToolOperation type does NOT match YAML reality.

types.ts defines: 'list' | 'detail' | 'statistics' | 'trend' | 'alert' | 'mutation'
YAMLs actually use: 'detail' | 'search' | 'statistics' | 'dashboard' | 'trend'

In types.tsIn YAMLsStatus
list(not used)DEAD TYPE
detaildetail (2 files)OK
statisticsstatistics (1 file)OK
trendtrend (1 file)OK
alert(not used)DEAD TYPE
mutation(not used)DEAD TYPE
(missing)search (7 files)TYPE ERROR
(missing)dashboard (1 file)TYPE ERROR

Impact: The TypeScript compiler will accept search and dashboard at runtime because YAML parsing bypasses type checking (raw.operation as ToolDefinition['operation'] is a cast, not a validation). But it means:
  • The matchScore operation check tool.operation === intent.operation will work for search and dashboard only if the intent extraction also outputs those values -- which it does, because the LLM reads the tool-selection-guide that uses these terms.
  • But the TypeScript type system provides zero safety here. Refactoring the operation values would not be caught by the compiler.
  • The tool-selection-guide table correctly lists search and dashboard as operation types, matching the YAML reality. So the LLM gets the right guidance. But the code is technically lying about its types.

Scoring Component Analysis

Domain Score (40 points) -- Binary, Not Proportional

The domain check is binary: if ANY domain in the intent overlaps with ANY domain in the tool, full 40 points are awarded. This means:

  • equipment.profile (6 domains) gets 40 points for almost ANY query involving equipment, fault, maintenance, patrol, spare, or lifecycle.
  • fault.search (1 domain: fault) gets 40 points only for fault-related queries.
  • A query about "故障趋势" (intent.domains = ["fault"]) gives 40 points to both fault.search and equipment.profile (because equipment.profile includes fault-repair domain).

Problem: Broad tools (equipment.profile, scope.overview, dashboard) consistently score high on domain, diluting the signal. The operation score (30 points) becomes the real differentiator.

Recommendation: Consider proportional domain scoring: 40 * (overlap_count / intent_domain_count). A fault-only query should score higher on fault.search (1/1 = 100%) than equipment.profile (1/6 = 17%).

Domain Naming Inconsistency Impact

Domain names are inconsistent across skills:

Domain ConceptUsed in Some SkillsUsed in Other Skills
Fault + Repairfault-repair (equipment.profile, repair.profile, scope.overview)fault + repair separately (dashboard, trend, fault.search, repair.search)
Anomalyanomaly (trend, anomaly.search)Not present in equipment.profile or scope.overview (though they return anomaly data)

Impact on matchScore: If the LLM intent extraction outputs domains: ["fault-repair"], the .some(d => tool.domains.includes(d)) check will match equipment.profile (which declares fault-repair) but will NOT match fault.search (which only declares fault) or repair.search (which only declares repair). Conversely, if intent says ["fault"], it will match fault.search but NOT equipment.profile (unless equipment.profile also lists fault separately -- it doesn't, it lists fault-repair).

This is a real routing bug. Depending on how the LLM names the domain in its intent, different tools get matched.

Operation Score (30 points) -- Effective but Relies on LLM Intent Accuracy

The 30-point operation bonus is the strongest differentiator in practice. When domain gives 40 to multiple tools, operation breaks the tie. This works well IF the LLM correctly identifies the operation type. The tool-selection-guide table helps.

Filter Score (20 points, proportional) -- Well Designed

Filter coverage is the only proportional component. If intent requires 3 filters and a tool supports 2 of them, score = 20 * (2/3) = 13.3. This correctly penalizes tools that lack needed filters. However, if intent.filters is empty (common for simple queries), all tools get 0 here, and it provides no differentiation.

Chain Score (10 points) -- Problematic

The chain score awards 10 points to any tool with non-empty feedsInto or dependsOn. This means:

ToolfeedsIntodependsOnChain Score
equipment.profile[][]0
repair.profile[][]0
scope.overview[eq.profile, eq.search][]10
equipment.search[eq.profile, fault.s, repair.s][]10
fault.search[repair.s, repair.profile, eq.profile][]10
repair.search[repair.profile, spare.s][]10
maintenance.search[eq.profile][]10
patrol.search[anomaly.s, eq.profile][]10
anomaly.search[fault.s, eq.profile][]10
spare.search[eq.profile, repair.profile][]10
dashboard[][]0
trend[][]0

Problem: This is backwards. Profile tools (the most complete, should-be-preferred tools) get 0 chain score, while search tools (intermediate, often stepping-stones) get +10. This biases scoring toward search over profile, opposite to the design intent expressed in base-instructions: "优先使用全景工具".

Recommendation: Either remove the chain score (it's only 10 points so impact is limited) or invert it: give bonus to tools that are TARGET of feedsInto chains (i.e., tools that other tools feed into, like equipment.profile which appears in many tools' feedsInto lists).

Key insight: The matchScore is currently a pre-filter, not the decision maker. The prompt assembler passes ALL tools to the LLM regardless of matchScore (see registry.ts: "P0: 不做阈值过滤，返回全部工具"). So the score's inaccuracies don't directly cause routing failures -- the LLM reads all tool descriptions and makes its own choice. But when matchScore is used for ranking or filtering in the future (P2/P3), these issues become critical.

4.1 system-prompt.md

Grade: A-

Single sentence, clear identity anchor. Anthropic recommends placing the role/persona at the start of the system prompt -- this follows that correctly. Deliberately system-agnostic (says "企业系统" not "EAM") for future multi-system support.

Minor suggestion: Could add the platform's core capability statement: "我能理解你的自然语言问题，调用相应工具获取数据，并给出分析。" This would help set user expectations about the interaction model (NL -> tools -> analysis).

5 Issues & Recommendations

Critical Priority

C1
when_to_use / when_not_to_use not injected into prompt
File: lib/brain/prompt-assembler.ts lines 97-102
The most valuable routing information in the YAML files is invisible to the LLM. The assembler only includes name, description, and parameter list. The when_to_use/when_not_to_use fields are parsed by yaml-loader but never used.
Fix: Add whenToUse and whenNotToUse to the tool description template in prompt-assembler.ts. Estimated impact: significant improvement in conflict resolution (patrol vs anomaly, profile vs search, scope vs equipment.search).
C2
ToolOperation type mismatch: types.ts vs YAML reality
File: lib/types.ts line 70
TypeScript type defines 'list' | 'detail' | 'statistics' | 'trend' | 'alert' | 'mutation' but YAMLs use 'search' and 'dashboard'. The as cast in yaml-loader.ts hides the error.
Fix: Update ToolOperation to 'detail' | 'search' | 'statistics' | 'dashboard' | 'trend'. Remove dead types (list, alert, mutation) or keep them for future use with a comment.
C3
Domain naming inconsistency causes matchScore routing bugs
Files: All YAML files
Some tools use fault-repair as a compound domain, others use fault and repair separately. The matchScore domain check is an exact string match, so "fault" !== "fault-repair". This means fault.search won't match an intent with domain "fault-repair", and equipment.profile won't match an intent with domain "fault".
Fix: Standardize domain names. Either: (a) always use separate domains (fault, repair) and update equipment.profile/scope.overview/repair.profile, or (b) implement substring/contains matching in calcMatchScore. Option (a) is cleaner.

Medium Priority

M1
trend.yaml missing supports_filters
File: skills/eam/trend.yaml
trend.yaml has no supports_filters field, causing it to score 0 on filter dimension. This leads to ties with fault.search on trend queries. Add: supports_filters: [domain, dateRange, groupBy, splitBy, equipment, productionLine, department].
M2
dashboard.yaml missing supports_filters
File: skills/eam/dashboard.yaml
Same issue as trend. Add: supports_filters: [format] (even though minimal, it should be explicit).
M3
scope.overview missing supports_filters
File: skills/eam/scope-overview.yaml
Same issue. Add: supports_filters: [identifier, format]. This would help scope.overview score non-zero on the filter dimension when the intent includes scope-related filters.
M4
Few-shot examples miss 4 search tools
File: prompts/few-shot-examples.json
equipment.search, repair.search, patrol.search, anomaly.search have zero few-shot coverage. Add at least 2 more examples: one for patrol vs anomaly disambiguation, one for equipment.search vs scope.overview disambiguation.
M5
Chain score is backwards
File: lib/tools/registry.ts lines 76-79
Profile tools (preferred per design) get 0 chain score; search tools get +10. Consider inverting: give bonus to tools that are TARGETS of feedsInto chains, or simply remove the chain component.
M6
rules.md Rule 4 ambiguity
File: prompts/rules.md
"只返回 JSON" could be interpreted as prohibiting natural language in the thought field. Rewrite to: "输出必须是严格的 JSON 对象（含 thought/calls 等字段），不要在 JSON 前后加非 JSON 文字。"
M7
Per-tool YAML examples not injected into prompt
File: lib/brain/prompt-assembler.ts
Each YAML has 2-3 tool-specific examples that demonstrate parameter usage. These are parsed but wasted. Consider injecting them as part of the tool description (compact format) or as additional few-shot entries.
M8
patrol.search status enum not documented
File: skills/eam/patrol-search.yaml
Unlike all other search tools that list exact status codes, patrol.search says "具体值参考系统定义". The AI cannot fill the status parameter reliably.

"传名称不传ID" and "一个工具能搞定就不要拆" appear in both files. Could save ~200 tokens by deduplicating. Not harmful -- redundancy reinforces the message.

few-shot example 3: WO-201 prefix mismatch
repair.profile describes RO/FR prefixes but the example uses "WO-201". Minor but sets incorrect expectation.
L3
react-instructions references {{N.path}} syntax
This appears to be a legacy reference from a previous parameter-chaining architecture. Either remove or explain it.
L4
rules.md Rule 5 is misplaced
"参数支持业务编号" is a tool design principle, not an AI behavioral rule. Move to tool-selection-guide.md.

No Anthropic API prompt caching

All other search tools support groupBy for aggregation statistics. spare.search lacks it. Not critical -- spare queries are less likely to need aggregation -- but inconsistent.
