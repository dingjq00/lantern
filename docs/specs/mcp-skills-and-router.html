1. Architecture Overview

端到端数据流

用户输入自然语言，经 LLM Router 选择 Skill，执行 MCP 工具获取数据，最终由 AI 总结为自然语言回答。

三层分离架构

2. 12 Skill Cards

每个 Skill 是一个 YAML 文件，声明了 AI 可以调用的一个能力单元。Skill 不执行逻辑，它是 AI 路由的"菜单项"—— 描述场景、边界、参数，映射到对应的 MCP 工具去执行。

Tier 1 — 实体全景画像 3 Skills

深度画像类。单一实体的全景数据，内部并行调用 7-9 个 API 自动聚合。适合"某台设备/某张工单/某个车间怎么样"。

eam.equipment.profile

Tier 1 Profile
获取单台设备的全景画像。输入设备名称、编号或 ID（任一均可），返回该设备的完整运营数据： 基础信息、KPI 指标、近期故障报修、维修工单、保养记录、巡检记录、BOM 备件清单（含实时库存）、生命周期事件。 内部会并行调用 9 个后端 API 并自动聚合，AI 无需逐一编排。 当匹配到多台设备时会返回候选列表，由 AI 追问用户确认。
Type: simple (1:1)
Maps to: eam.equipment.profile
Operation: detail
Quality: 95
Cost: medium (9 APIs)
equipment fault-repair maintenance patrol spare lifecycle
Input Parameters
参数名类型说明
identifier* string 设备标识符，接受三种形式（Poka-yoke）：设备编号如 "CNC-001"、设备名称如 "数控车床"、数字 ID 如 "101"。匹配策略：精确 > 前缀 > 包含，多结果返回候选列表（最多 5 个）。
format string detailed（默认，全景含 KPI+故障+维修+保养+巡检+BOM+生命周期）| concise（仅基础信息+KPI）
When to Use
  • 用户问某台设备的综合状况："CNC-001 怎么样""数控车床什么情况""这台设备最近怎么了"
  • 用户需要某台设备的详细信息："设备 EQ-042 的详情""3号注塑机的完整资料"
  • 用户问某台设备的故障/维修/保养/巡检历史
  • 用户问某台设备的 BOM 或备件库存
  • 需要设备画像作为分析基础（如对比两台设备差异，对每台调一次）
When NOT to Use
  • 查多台设备列表或筛选设备 → eam.equipment.search
  • 某个车间/产线/部门的整体情况 → eam.scope.overview
  • 全局系统概况或总数 → eam.dashboard
Examples
"CNC-001 这台设备最近怎么样？" identifier: "CNC-001", format: "detailed"
"快速看下数控车床的状态" identifier: "数控车床", format: "concise"
"设备 ID 101 的 BOM 清单和备件库存" identifier: "101", format: "detailed"

eam.repair.profile

Tier 1 Profile
获取单张维修工单的全景画像。支持三种入口：维修工单号（RO 开头）、故障报修号（FR 开头，自动追溯关联工单）、数字 ID。 返回完整维修链路：工单基础信息、关联故障报修、设备信息、备件使用明细、工时明细、知识引用、出库单、操作日志。 内部并行调用 7 个后端 API 自动聚合。
Type: simple (1:1)
Maps to: eam.repair.profile
Operation: detail
Quality: 95
Cost: medium (7 APIs)
fault-repair spare knowledge
Input Parameters
参数名类型说明
identifier* string 维修工单号如 "RO202603110001"、故障报修号如 "FR202603260105"（自动追溯）、数字 ID 如 "5023"
format string detailed（默认，全链路含备件+工时+知识+出库+日志）| concise（仅工单基础+故障摘要+设备名称）
When to Use
  • 问某张维修工单详情："RO202603110001 什么情况""这个工单进展如何"
  • 从故障报修追踪维修进展："FR202603260105 修了没有"
  • 问维修用了哪些备件或花了多少工时
  • 问维修过程参考了什么知识/经验
  • 分析单张工单的完整维修链路：故障→报修→分配→维修→用件→完工
When NOT to Use
  • 查多张工单列表或按条件筛选 → eam.repair.search
  • 某台设备的综合状况（不仅维修） → eam.equipment.profile
  • 维修相关统计趋势 → eam.trend
Examples
"维修工单 RO202603110001 的详细情况" identifier: "RO202603110001", format: "detailed"
"报修单 FR202603260105 修好了没有？" identifier: "FR202603260105", format: "detailed"
"快速看下工单 5023 的状态和负责人" identifier: "5023", format: "concise"

eam.scope.overview

Tier 1 Profile
获取某个组织/空间范围的概览画像。输入车间名、产线名、部门名或区域名， MCP 自动在三棵树中匹配（优先级：产线 > 部门 > 位置），无需 AI 判断属于哪棵树。 返回该范围下的设备列表与状态分布、故障汇总、维修汇总、保养完成率、异常汇总。 只展开直接下级，不递归展开孙级（避免数据爆炸）。
Type: simple (1:1)
Maps to: eam.scope.overview
Operation: statistics
Quality: 90
Cost: high (4 域并行)
equipment fault-repair maintenance patrol
Input Parameters
参数名类型说明
identifier* string 产线名如 "A线"、部门/车间名如 "一车间"、区域名如 "厂区A"。MCP 自动识别属于哪棵树，匹配优先级：产线 > 部门 > 位置。
format string detailed（默认，含设备清单最多 50 台）| concise（仅汇总指标，适合多范围对比）
When to Use
  • 某个车间/产线/部门的整体情况："一车间怎么样""A线概览""机加车间设备情况"
  • 某个范围的设备健康度："注塑产线有多少设备在运行"
  • 某个范围的维修/保养/巡检汇总："二车间保养完成率多少"
  • 对比两个范围（对每个范围调一次，用 concise 模式）
  • 管理层日常巡查："生产部下面各车间今天什么情况"
When NOT to Use
  • 全局/全厂概况（不是某个具体范围） → eam.dashboard
  • 某台具体设备的详情 → eam.equipment.profile
  • 按复杂条件筛选设备 → eam.equipment.search
Examples
"一车间目前的设备运行情况怎么样？" identifier: "一车间", format: "detailed"
"A线和B线哪个故障更多？" identifier: "A线", format: "concise"
"研发部有多少设备？保养完成率多少？" identifier: "研发部", format: "detailed"
Tier 2 — 搜索与筛选 7 Skills

列表搜索类。按多维条件过滤，支持 groupBy 聚合统计。适合"查看列表""统计分布""按条件筛选"。

eam.equipment.search

Tier 2 Search
按条件搜索设备列表，支持按状态、分类、产线、部门、位置、重点设备过滤，可按维度聚合统计（设备数量分布）。 设备是 EAM 的引力中心，几乎所有搜索的起点。
Type: simple (1:1)
Maps to: eam.equipment.search
Operation: search
Quality: 85
Cost: low
equipment
参数名类型说明
statusinteger设备状态码：0=待验收 1=运行中 2=维修中 3=停机 4=封存 5=待整改 6=闲置 7=报废
categorystring设备分类名称或ID（如"注塑机""CNC"）
productionLinestring产线名称或ID（如"A线"）
departmentstring部门/车间名称或ID
locationstring安装位置名称或ID
isKeyboolean是否仅查重点/关键设备
dateRangeobject时间范围过滤（{from, to}）
groupBystring聚合维度：status / category / department
formatstringdetailed | concise
limitinteger返回条数上限，默认20
When to Use
  • 查看符合条件的设备列表："维修中的设备有哪些""A线有多少设备"
  • 设备统计分布："各状态设备数量""按部门统计设备"
  • 筛选重点设备："重点设备清单""关键设备有哪些"
  • 按分类查设备："注塑机有多少台""CNC设备列表"
When NOT to Use
  • 某台设备完整档案 → eam.equipment.profile
  • 全局仪表盘数字 → eam.dashboard
  • 某范围的综合画像 → eam.scope.overview
Examples
"维修中的设备有哪些？" status: 2, format: "concise"
"A线各状态设备数量统计" productionLine: "A线", groupBy: "status"
"一车间的重点设备清单" department: "一车间", isKey: true, format: "detailed"

eam.fault.search

Tier 2 Search
按条件搜索故障报修列表，支持按设备、产线、部门、故障状态、紧急程度、故障类型、时间范围过滤，可按维度聚合统计。 故障是 EAM 的核心事件流，故障→维修 是最重要的业务链条。
Type: simple (1:1)
Maps to: eam.fault.search
Quality: 85
Cost: low
fault
参数名类型说明
equipmentstring设备名称/编号/ID（智能解析）
productionLinestring产线名称或ID
departmentstring部门/车间名称或ID
statusinteger0=待审核 1=待接单 2=维修中 3=挂起 4=待验收 5=已完成 6=已关闭 7=已拒绝 8=已撤回
urgencyinteger0=一般 1=紧急 2=特急
faultTypestring故障类型如"机械故障""电气故障"
dateRangeobject故障上报时间范围（{from, to}）
groupBystringequipment / status / urgency
format / limitstring / int返回格式与条数
When to Use
  • 查看故障列表/数量："上月有多少故障""最近一周的故障记录"
  • 按设备/产线查故障："CNC-001的故障记录""A线故障情况"
  • 关注紧急故障："有哪些特急故障""紧急故障有多少"
  • 统计故障分布："哪台设备故障最多""各状态故障数量"
When NOT to Use
  • 故障关联的维修工单详情 → eam.repair.search / eam.repair.profile
  • 某台设备完整档案 → eam.equipment.profile
  • 故障数量时间趋势 → eam.trend
Examples
"上个月A线有多少故障？" productionLine: "A线", dateRange: {from: "2026-02-01", to: "2026-02-28"}
"哪台设备故障最多？按设备统计一下" groupBy: "equipment"

eam.spare.search

Tier 2 Search
备件搜索，支持两种模式：(1) BOM 模式——传 equipment 参数，返回该设备备件清单及库存； (2) 通用模式——按名称/编号/分类/库存预警过滤。每个备件返回库存量、上下限、是否低于安全库存、关联设备数。 备件是横切域，同时关联维修和库存。
Type: simple (1:1)
Maps to: eam.spare.search
Quality: 85
Cost: medium
spare
参数名类型说明
identifierstring备件名称或编号（通用搜索模式）
equipmentstring设备名称/编号/ID（BOM 模式，优先级最高）
categorystring备件分类

3. Router Architecture

Router 是平台的核心编排器（lib/brain/router.ts），实现 ReAct 循环——think/execute/observe/think again。 统一流程无需预判复杂度：规划→执行→观察→决定是否追查。

ReAct 循环流程

// processQuery() — 核心入口，最多 3 次 think（规划→审查放开→finish）

START
  │
  ├── assemblePrompt() — 六层架构组装 System Prompt
  │     ├── Layer 1: System Prompt（你是谁）
  │     ├── Layer 2: Rules（底线约束）
  │     ├── Layer 3: Task Instructions（ReAct 模板 + 工具选择指南）
  │     ├── Layer 4: Few-shot Examples
  │     ├── Layer 5: Dynamic Context（可用工具描述 + verdict + 用户上下文）
  │     └── Layer 6: User Input
  │
  ├── while (!finished && round <= 2)     // MAX_CHASE_ROUNDS = 2
  │     │
  │     ├── THINK ── llm.think(messages)
  │     │     ├── 首轮(round=0): extractIntent → 计算 intentHash → 查 verdict
  │     │     ├── 返回 calls[] = [{tool, arguments}, ...]
  │     │     └── 返回 finish: true/false, thought: "推理过程"
  │     │
  │     ├── [超纲检测]
  │     │     ├── unsupported 或首轮无 calls?
  │     │     ├── → ESCALATE: llm.think(messages, "gpt-5.4")
  │     │     └── 强模型也无法处理 → 返回上下文相关的超纲回复
  │     │
  │     ├── EXECUTE ── 遍历 calls[]
  │     │     ├── resolveArgRefs() — 解析 {{N.path}} 参数引用
  │     │     ├── registry.execute(tool, args) — MCP 执行
  │     │     └── trace.addCall() — 记录每次调用（工具/参数/结果/耗时）
  │     │
  │     ├── OBSERVE ── 注入观察到消息上下文
  │     │     ├── 事实对比: 用户问什么 vs 已获得什么字段
  │     │     └── "按 5 步模板继续推理。如果已覆盖用户问题则 finish。"
  │     │
  │     └── round++
  │
  ├── computeConfidence() — 三信号融合
  │     ├── toolMatch:      全部成功=high, 部分=medium, 全失败=low
  │     ├── verdictConfidence: sample>=10 → high, 3-9 → medium, <3 → low
  │     └── queryClarity:    从 intent 提取
  │     // 规则: 3×high→high, 任一low→low, 其余→medium
  │
  ├── llm.summarize() — AI 分析数据，生成自然语言回答
  │
  ├── evaluateWithSubagent() — 自学习: 子代理评估结果质量
  │     └── quality != 'good' → insertLesson()
  │
  └── RETURN StructuredResult
        ├── answer (自然语言)
        ├── data (原始数据)
        ├── confidence (high/medium/low)
        ├── sources (数据来源)
        ├── trace (完整调用链路)
        └── lessonEval (自学习评估)

5. 6-Layer Context Integration

Prompt 由 prompt-assembler.ts 按六层架构组装。前四层是静态内容（可缓存），后两层是动态内容（每次请求变化）。 Skill 描述注入在 Layer 5（可用工具），是 AI 路由决策的核心依据。

1
System Prompt
角色定义——你是 EAM 智能助手，会调用工具获取数据并分析
Static
2
Rules
底线约束——不编造数据、不执行危险操作、诚实回答不确定性
Static (High Attention)
3
Task Instructions
ReAct 模板（5 步结构化思维: ToolGT + Step-Back + Reflexion）+ 工具选择指南
Static
4
Few-shot Examples
编排示例——展示 Round 0 规划 + 观察 + Round 1 追查的完整流程
Static (Occasional Update)
---- 缓存边界 ----
5
Dynamic Context
Skill 描述（12 个工具的 name/description/parameters）+ Verdict（历史推荐路径）+ Session Memory（对话上下文）+ 当前环境（系统/域/工具数/日期）
Dynamic (per-request)
6
User Input
用户的自然语言查询（单独作为 user message，不在 system prompt 里）
Dynamic (per-request)

Skill 描述如何注入 Prompt

// prompt-assembler.ts — Layer 5 生成过程

const toolDescriptions = tools.map(t => {
  const params = Object.entries(t.inputSchema.properties)
    .map(([k, v]) => `  - ${k} (${v.type}): ${v.description}`)
    .join('\n')
  return `- **${t.name}**: ${t.description}\n${params}`
})

// 最终注入 System Prompt 的 "## 可用工具" 部分:
// - **eam.equipment.profile**: 获取单台设备的全景画像...
//     - identifier (string): 设备标识符，接受三种形式...
//     - format (string): 返回详细程度...
// - **eam.fault.search**: 按条件搜索故障报修列表...
//     - equipment (string): 设备名称、编号或ID...
// ... (12 个工具)

// Verdict 注入（如果有历史推荐路径）:
// ## 历史推荐路径
// eam.equipment.profile（评分 4.2，15 次样本）

设计原则

  • 静态在前（可缓存），动态在后 — Layers 1-4 永不变或少变，可利用 LLM 的 Prompt Cache
  • Rules 最靠前 — 位置越靠前，Attention 权重越高，底线约束不可被后续内容覆盖
  • Skill 描述是唯一的工具发现机制 — AI 不知道有哪些 API，它只看到 Skill YAML 生成的描述
  • Verdict 是经验传递机制 — 历史同类查询的推荐路径，让 AI 站在前人肩上

6. Self-Learning Vision

Skill YAML 不只是静态配置，它是自学习闭环的进化节点。通过 Audit Trail + 外部反馈信号驱动 Skill 优化， 让路由准确率随使用自动提升。核心原则：信号必须来自外部，AI 自评无效（架构原则 #3）。

Skill YAML 是自学习的关键杠杆

修改一个 YAML 文件 = 改变 AI 的路由行为。这是刻意设计的：

  • 声明式 — 非工程师也能理解和修改 when_to_use / when_not_to_use
