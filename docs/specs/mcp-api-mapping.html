1. 公共解析方法（所有工具共用）

identifier 智能解析封装在 MCP 内部，AI 层完全不碰。三个解析方法 + 一个匹配策略。

// 所有工具共用的 identifier → ID 解析 resolveEquipment(identifier: string) → GET /eam/equipment/page?keyword={identifier}&pageSize=5 → 返回 { id, equipmentCode, equipmentName } 或 candidates[] resolveProductionLine(identifier: string) → GET /eam/production-line/page?keyword={identifier}&pageSize=5 → 返回 { id, lineCode, lineName } 或 candidates[] resolveDepartment(identifier: string) → GET /system/dept/list?name={identifier} → 返回 { id, name, parentId } 或 candidates[] 匹配策略: exact match > startsWith > contains 唯一匹配 → 返回实体 多个匹配 → 返回候选列表（最多 5 个），AI 追问用户

productionLine / department 过滤（公共逻辑）

大部分业务 API 只支持 equipmentId 过滤，不支持直接按产线/部门过滤。MCP 内部做两步过滤：

Step 1: 解析产线/部门 → 查该范围下的设备 ID 列表
  产线: /production-line/equipment/list?lineId= → 设备 ID 列表
  部门: /equipment/page?deptId= → 设备 ID 列表
Step 2: 用设备 ID 列表过滤业务数据（如 /fault-report/page?equipmentId=）
优化: 如果设备数太多，改用服务端 IN 查询或分批处理

Tier 1 eam.scope.overview

输入 identifier → 三棵树匹配 → 查设备列表 → 各域汇总。最复杂的工具。

Step 1: 层级解析（三棵树顺序匹配） ProductionLine: GET /eam/production-line/page?keyword={identifier} Department: GET /system/dept/list?name={identifier} Location: GET /eam/location/tree → 遍历匹配 name 优先级: ProductionLine > Department > Location Step 2: 获取设备列表 产线: GET /production-line/equipment/list?lineId= → equipmentIds GET /equipment/page?ids=... → 设备详情 部门: GET /equipment/page?deptId= → 直接获取 位置: GET /equipment/page?locationIds= → 直接获取 Step 3: 各域汇总（基于设备 ID 列表，并行调用） 故障: GET /fault-report/page?equipmentId=... → 按设备统计 维修: GET /repair-order/page?equipmentId=... → 按状态统计 保养: GET /maintenance/task/page?equipmentId=... → 完成率 巡检: GET /patrol/task/analytics/by-equipment → 异常率 备件: GET /spare/alert/list → 过滤该范围设备 Step 4: 下级分项 车间级 → 查该部门下的产线列表，每条产线各自汇总 只展开直接下级，不递归

Gap: 0（API 都存在）。但实现复杂度高——需要多阶段调用，设备数多时要分批。

丰富化（中等丰富度）— 每条工单需额外调用:

丰富化项API说明
备件费用汇总/repair-order/spare/listsum(quantity × unitPrice)

性能风险: 20 条工单 × 4 个丰富化调用 = 80 个 API 调用。
解法: concise 模式只返回主 DO 字段（含 repairMinutes/laborCost/materialCost 已有汇总）；detailed 模式限制 limit=10 并行调用。
更优方案: 推动 EAM 后端加 orderType + dateRange 到 PageReqVO，加批量丰富化接口。

按域查询时间序列数据。大部分域没有原生趋势 API，MCP 需从列表数据聚合。

域原生趋势 API回退方案状态

maintenance 保养无/maintenance/task/page + MCP 聚合❌ 全靠 MCP

/patrol/task/analytics/by-equipment
/patrol/task/analytics/by-plan		自定义日期范围时用 /page✅ 较好

核心问题: 6 个域中只有巡检有较好的原生分析 API。其余 5 个域的趋势数据需要 MCP 从 page 列表拉数据后自己做时间聚合。
长期方案: 推动 EAM 后端为各域加分析端点（支持 dateRange + groupBy day/week/month）。
