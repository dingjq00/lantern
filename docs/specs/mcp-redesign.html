Insight68 MCP 工具层重新设计

从 22 个 API Wrapper 到 12 个意图级工具 — 让 MCP 主动服务 AI
Insight68 NL-API Platform 2026-03-28 状态: 设计审核中

1. 设计哲学

MCP 不应该躺平，应该主动服务于 AI。

🧠

确定性 MCP 做

ID 解析、同域多表聚合、层级定位 — 这些有明确答案的操作不该让 AI 猜

🎯

AI 只做判断

意图理解、跨域编排、分析对比 — 这些需要推理的才是 AI 的价值

👤

用户意图粒度

不按 API 设计，不按数据表设计，按"用户想知道什么"设计

业界验证

2026-03-28 调研确认，设计方向与 Anthropic 官方 + Context Engineering 前沿完全吻合。

来源核心观点对应我们的设计
Anthropic — Writing Tools for Agents "More tools don't always lead to better outcomes" — 合并自然连续的操作，不要 1:1 包装 API 22 → 12 工具合并
同上 工具描述优化比 system prompt 优化效果更大（SWE-bench 实测） 原则 #8: 描述 = Prompt 工程
同上 Poka-yoke 防错：接受宽松输入，减少模型犯错 原则 #1: identifier 智能解析
同上 response_format 参数：让 AI 按需选择 DETAILED vs CONCISE 原则 #7: format 参数
Context Engineering Part 2 100+ 工具会导致 Context Confusion — 保持 ~20 个核心工具，复杂链用代码解决 12 工具 + MCP 内部做确定性逻辑
DDD for MCP Servers 按业务域组织，每个 MCP Server = Bounded Context Tier 2 按域分 + 层级前缀命名

分工边界

谁做做什么例子
MCP 确定性动作：获取数据、ID 解析、同域聚合、层级导航 "E02" → 解析出设备 → 返回全景
"一车间" → 定位部门 → 聚合该范围数据
AI 非确定性能力：意图理解、跨域编排、分析/统计/对比 判断用户问的是维修还是保养
对比两台设备的故障率

3. 工具详细设计（12 个）

命名规范

采用 eam.<domain>.<action> 层级前缀命名。扩展到其他系统时自然分隔：mes.xxx / wms.xxx。

Tier 1 · 实体全景 — 3 个

围绕 schema 的聚合中心，一次调用返回完整画像。

eam.equipment.profile

设备全景

给定任意设备标识符，返回该设备的完整画像。MCP 内部完成 ID 解析和多域聚合。

参数类型说明
identifierstring"E02" / "EQ-001" / 数字ID — MCP 自动在 name/code/id 中匹配
formatstring?"detailed"(默认) | "concise" — concise 只返回基础+KPI，省 token
返回: ├ 基础: code, name, category, location, status, 负责人, 产线, 部门 ├ KPI: 故障次数, 平均修复时间, 保养完成率 ├ 近 5 条故障报修（带状态） ├ 进行中的维修工单 ├ 近 5 条保养任务（带完成状态） ├ 近 5 条巡检记录（带异常数） ├ BOM 备件清单 + 当前库存水位 └ 生命周期事件（采购→验收→变更）

覆盖场景: "E02 怎么样" "EQ-001 详细信息" "EQ-003 生命周期" "BOM 哪些库存不足"

eam.repair.profile

维修工单全景

给定工单标识符，返回完整维修工单画像。一个调用替代原来的 3 步查询。

参数类型说明
identifierstring"WO-005" / "FR-001" / 数字ID — 支持 orderCode、faultReportCode、ID 三种入口（Poka-yoke）
formatstring?"detailed"(默认) | "concise" — concise 省略日志和完整备件明细
返回: ├ 工单: code, status, type(内修/外协), 负责人, 时间线 ├ 关联故障报修（报修人, 故障描述, 紧急度） ├ 设备基础信息（code, name, 产线, 位置） ├ 备件使用明细（件号, 名称, 数量, 单价, 仓库） ├ 工时明细（人员, 工时, 费用） ├ 知识引用（文档标题, 类型） ├ 出库单（仓库名, 金额） └ 操作日志

覆盖场景: "WO-001 用了哪些备件" "WO-005 出库涉及哪些仓库" "维修参考了哪些文档"

eam.scope.overview

范围概览（层级自适应）

给定任意层级标识符，MCP 在三棵树中自动匹配（优先级: ProductionLine > Department > Location）。只展开直接下级，不递归。concise 模式不含设备清单，设备列表 limit 默认 50。

参数类型说明
identifierstring"一车间" / "A产线" / "制造部" / 区域名 — 三棵树模糊匹配
formatstring?"detailed"(默认) | "concise" — concise 只返回汇总指标，不含设备清单
返回: ├ 定位: 名称, 层级类型(部门/区域/产线), 上级, 下级列表 ├ 设备汇总: 总数, 按状态分布 ├ 故障汇总: 本月新增, 按紧急度分布 ├ 维修汇总: 进行中数, 本月完成数, 平均修复时间 ├ 保养汇总: 完成率, 逾期数 ├ 巡检汇总: 异常率, 最近异常设备 ├ 备件预警: 该范围设备 BOM 中库存不足的备件 └ 下级分项概览（如车间→按产线各自的指标）

覆盖场景: "一车间状态" "A线三项概览" "制造部概览"

4. 统一设计原则（12 条）

  1. identifier 智能解析 — 所有工具的 equipment / productionLine / department 参数接受 name/code/ID，MCP 内部模糊匹配后确定实体。来源: Anthropic Poka-yoke 防错设计
  2. 层级自动识别 — scope_overview 在 Department树/Location树/ProductionLine 中自动匹配层级，AI 不需要判断用户说的是部门还是产线
  3. 结果自带上下文 — 不返回裸 ID，所有返回数据带设备名/产线名/负责人等人类可读信息。来源: Anthropic "return only high signal information"
  4. search 中等丰富度 — 子表返回摘要/名称列表，不返回完整明细。需要明细时用 profile 工具
  5. search 支持 groupBy — 可选参数，MCP 内部聚合返回统计结果。groupBy 结果默认按 count 降序排列
  6. 权限透传 — 带用户 token 调 EAM API，后端框架自动按 dept_id 过滤数据（5 级 dataScope）
  7. response_format 参数 — 所有工具（不只是 Tier 1）支持 format: "detailed" | "concise"。AI 按需控制返回量。来源: Anthropic 工具设计指南
  8. 工具描述 = Prompt 工程 — 每个工具的 description / when_to_use / when_not_to_use 要精心打磨。来源: Anthropic 实测 — 优化工具描述比优化 system prompt 效果更大
  9. 层级前缀命名 — eam.<domain>.<action> 格式。扩展时 mes.xxx / wms.xxx 自然分隔。来源: Anthropic 推荐 prefix/suffix-based namespacing
  10. 多匹配策略 — identifier 匹配到多个实体时: exact match > startsWith > contains。仍有多个则返回候选列表（最多 5 个），由 AI 追问用户确认。
  11. scope_overview 匹配优先级 — ProductionLine > Department > Location。EAM 语境下用户更常按产线/部门说话，较少按物理位置。
  12. search 统一参数集 — 所有 search 工具统一支持 format / sortBy / sortOrder(asc|desc) / limit。维度参数（productionLine / department）尽量对齐。

5.5 工具边界定义

审查中发现的边界模糊点，在此明确定义。

边界定义
eam.dashboard vs eam.scope.overview dashboard = 全局指标快照（数字为主，跨域汇总，无设备清单）。"系统概况""总共多少设备" → dashboard
scope_overview = 范围画像（含设备清单、下级分项、更像"报告"）。"一车间怎么样""A线概览" → scope_overview
eam.scope.overview 数据量控制 只展开直接下级（不递归）
concise 模式不含设备清单，只有指标
设备列表 limit 默认 50
eam.repair.profile 多入口 接受三种标识符: orderCode ("WO-005") / faultReportCode ("FR-001") / 数字 ID
MCP 内部自动判断类型并解析（Poka-yoke — 不要求用户知道工单号才能查工单）
identifier 多匹配处理 匹配策略: exact match > startsWith > contains
仍有多个候选 → 返回列表（最多 5 个），由 AI 追问用户
精确匹配到唯一结果 → 直接返回数据
search profile vs search profile = 单个实体全景（深度，一个实体的全部关联信息）
search = 多个实体列表（广度，每条中等丰富度，支持过滤和聚合）
"WO-005 用了什么备件" → profile；"上月的维修工单" → search

8. P3 展望：API Schema 推断引擎

EAM 是第一个手工走通"Schema → MCP 设计"的案例。对于没有源码的系统，通过 API 抓包也能推断出 schema：

抓包(HAR/mitmproxy) → API 录制 → Schema 推断引擎 → 实体关系图 → MCP 工具设计 推断能力： URL 路径模式 → 实体名 + CRUD 操作 响应 JSON 字段 → 字段名、类型 xxxId 字段 → 外键关系 → 实体间连接 parentId → 树形结构 status 值域 → 状态机 / 枚举

这是 Insight68 从"做一个 EAM"到"做任何企业系统"的关键基础设施。EAM 手工走通后抽象成标准化工具。
