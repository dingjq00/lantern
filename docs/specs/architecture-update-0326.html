1.2 完整执行流（5 步模板 + 参数引用 + 三步 think + 级联 + 总结）

这是每个用户查询从输入到输出的 完整路径，对应 lib/brain/router.ts 的 processQuery() 函数。

用户查询
  |
  v
+-- Prompt 组装 (prompt-assembler.ts) ---------------------------+
|                                                                 |
|  base-instructions.md  -- 规则 + 时间映射 + 参数说明             |
|  + 系统上下文           -- 从工具 YAML 推断 (EAM, 6 域, 22 工具) |
|  + react-instructions.md -- 5 步模板 + 参数引用 + 输出格式       |
|  + 工具描述             -- 标准 MCP 格式 (name + desc + params)  |
|  + tool-selection-guide.md -- 通用方法论 (无 EAM 特有内容)       |
|  + few-shot-examples.json  -- 4 个编排示例 (ReAct 格式)         |
|  + (可选) verdict 推荐路径                                       |
|  + (可选) 用户上下文 (对话历史)                                   |
|                                                                 |
+-----------------------------------------------------------------+
  |
  | messages = [system: prompt, user: query]
  v
+-- ReAct 循环 (router.ts, 最多 3 次 think) ---------------------+
|                                                                 |
|  think-1 (规划): LLM 按 5 步模板推理                             |
|    [意图] -> [候选] -> [审查] -> [规划] -> [验证]                 |
|    输出: { thought, intent, clarity, calls: [...] }             |
|                                                                 |
|    * 如果 unsupported 或无 calls -> 级联升级到 gpt-5.4           |
|    * 级联也失败 -> 真正超纲，返回反问选项                         |
|                                                                 |
|  执行 calls (按序, 支持 {{N.path}} 参数引用):                    |
|    call[0] 执行 -> 解析 {{0.xxx}} -> call[1] 执行 -> ...        |
|    每个 call 记录到 trace                                        |
|                                                                 |
|  观察注入 (Reflexion 式事实对比):                                 |
|    "用户问: X, 已获得字段: Y, 按 5 步模板继续推理"               |
|                                                                 |
|  think-2 (审查): LLM 看到结果后判断                              |
|    覆盖 -> { finish: true }                                     |
|    不覆盖 -> { calls: [补充工具] } -> 执行 -> 注入观察           |
|                                                                 |
|  think-3 (finish, 仅复杂题需要):                                 |
|    { finish: true }                                             |
|                                                                 |
+-----------------------------------------------------------------+
  |
  v
+-- 置信度计算 (confidence.ts) ----------------------------------+
|  toolMatch: high (默认, P1 未启用 matchScore)                   |
|  verdictConfidence: 从 verdict 表 sampleCount 计算              |
|  queryClarity: 从 LLM clarity 输出映射                          |
|  融合: 3 high -> high / 任一 low -> low / 其余 medium           |
+-----------------------------------------------------------------+
  |
  v
+-- LLM 总结 (codex-proxy.ts summarize) -------------------------+
|  输入: 合并的工具数据 + 用户原始问题 + 展示格式提示              |
|  反编造规则: "只能基于提供的数据, 宁可说数据不足也不编造"         |
|  输出: { answer, display, columns, followUp }                   |
+-----------------------------------------------------------------+
  |
  v
+-- 写入存储 (异步) ---------------------------------------------+
|  session -> nl_memory_sessions                                  |
|  trace   -> nl_traces                                           |
|  lesson  -> 由外部信号触发 (不做 AI 自评)                        |
+-----------------------------------------------------------------+
  |
  v
返回 StructuredResult { answer, data, display, confidence, sources, trace }

1.3 Prompt 文件与角色

文件 角色 关键内容
prompts/base-instructions.md 基础规则 只用清单中的工具、允许多步编排、参数支持业务编号、时间映射规则、"表达意图不展开循环"
prompts/react-instructions.md ReAct 推理模板 5 步结构化模板: [意图] [候选] [审查] [规划] [验证]。参数引用语法 {{N.path}}。首轮/审查轮/finish 三种 JSON 输出格式。域覆盖 + 数据覆盖双检查
prompts/tool-selection-guide.md 通用工具选择方法论 5 步方法: 理解上下文 -> 分析意图 -> 选工具 -> 拿到数据自己分析 -> 注意事项。零 EAM 特有内容，纯方法论
prompts/few-shot-examples.json ReAct 编排示例 4 个示例覆盖: 单工具直查、依赖引用({{0.xxx}})、并行查询、多轮追查。全部使用 5 步模板格式

1.4 Router 级联策略

级联(escalation)是 P1 最大的准确率贡献者（+16pp），实现在 router.ts 中：

think-1 (gpt-5.4-mini)
  |
  +-- 有 calls -> 正常执行
  |
  +-- unsupported 或 无 calls
        |
        v
      think-1-retry (gpt-5.4, 强模型)
        |
        +-- 有 calls -> 用强模型结果继续
        |
        +-- 仍然 unsupported -> 确认超纲，返回反问选项

级联只在首轮触发，不在审查轮触发。强模型用于兜底 mini 搞不定的复杂题，不影响简单题的速度和成本。

1.5 Benchmark 结果

测试条件：40 题测试集（L1-L5 五级难度），通用架构（零 EAM 查找表），gpt-5.4-mini + gpt-5.4 级联。Ground Truth 经过审查修正（8 题 GT 修正 + 6 组等效路径）。

难度 题数 Recall 说明
L1 (单工具直查) 10 100% 全对
L2 (有筛选条件) 10 95% 1 题参数错误
L3 (跨工具依赖) 6 83% 1 题遗漏一步
L4 (跨域组合) 7 82% 复杂域组合偶尔遗漏
L5 (分析推理) 7 86% 需要 AI 分析能力的题表现好
总计 40 90.6%

Part 2: 与原始设计的差异

P1 设计文档 (docs/superpowers/specs/2026-03-26-p1-design.md) 在编码和调优过程中经历了多次实质性变更。以下是每个变更点的"原始设计 vs 实际实现"对比。

2.1 ReAct: "每轮一个工具" --> 批量调用 + 参数引用

原始设计

标准 ReAct 循环: 每轮思考 -> 选一个工具 -> 执行 -> 观察 -> 下一轮。最多 3 轮追查（共 4 轮 think）。

实际实现

批量调用 + 参数引用: 首轮一次性规划完整链路（可多个工具），用 {{N.path}} 表达依赖关系。三步 think（规划 -> 审查放开 -> finish），简单题 2 次 think 就结束。

为什么改：标准 ReAct 每轮只选一个工具，一个"设备EQ-001的维修记录"就要 3 轮 think（查设备 -> 拿 ID -> 查维修）。参数引用让有依赖的工具一轮全部规划完，router 按序执行并自动传参。Benchmark 显示追查轮过多有害（3 轮追查时 AI 重复调失败工具），1-2 轮就够。

2.2 自学习: Verdict Winner --> Lesson --> AI 自评无效 --> 外部信号

原始设计

verdict 系统: 同类查询累积 5 条 -> LLM evaluate -> 计算 winner 工具链 -> 下次注入推荐路径。Thumbs Up/Down 权重 x3。

实际实现

verdict 代码存在但 被证明无效: 60% 准确率下积累的 40% 是错误经验。AI 自评(lesson)也无效: 同一个脑子犯的错自评发现不了。当前状态: 只存 session/trace，不做自动学习。注释写明"lesson 由外部信号触发"。

演进路径：

  1. 最初方案: verdict winner recording（记录哪个工具链最优）
  2. 发现问题: 60% 准确率下积累的是错误经验，越学越歪
  3. 替代方案: lesson 系统（记录错误教训而非正确答案）
  4. 实现了 AI 自评 generateLesson()，但发现循环论证 -- 同一个 LLM 犯错后自评也发现不了错误
  5. 结论: 有效学习信号必须来自外部（用户反馈、结果质量检测、Ground Truth）

dingjq 原话："正确的积累，反而没有那么重要。" 从错误中学习比记录正确答案更有价值。

2.3 Guide: EAM 查找表 --> 通用方法论

原始设计 (EAM 查找表)

tool-selection-guide.md 包含 EAM 域的查找表: "问到设备 -> 用 query_equipment"、"问到故障 -> 用 query_fault_reports"。Benchmark 88%。

实际实现 (通用方法论)

guide 零 EAM 特有内容: 5 步方法论（理解上下文 -> 分析意图 -> 选工具 -> 自己分析 -> 注意事项）。Benchmark 从 60% 经过级联+模板补回到 90.6%。

为什么改：查找表 88% vs 通用 guide 60%，28pp 差距是"作弊分" -- 查找表里写的就是 Ground Truth 的答案，换个系统就全废了。通用方法论确保架构可迁移到任何企业系统。用级联(+16pp) + 5 步模板 + 参数引用补回了大部分差距。

2.4 工具描述: YAML 全量元数据 --> 标准 MCP 格式

原始设计

注入 YAML 的完整元数据: name, description, domains, operation, supports_filters, returns, feeds_into, depends_on, when_to_use, when_not_to_use, examples...

实际实现

标准 MCP 格式: name + description + inputSchema.properties。工具间链路关系写在 description 的自然语言中（"list 工具不含 X，需要本工具补全"），不用结构化的 feeds_into/depends_on。

为什么改：LLM 理解自然语言描述比结构化标签更准确。把链路关系嵌入 description 比用 feeds_into 字段更直接。YAML 中的额外字段（domains, operation, supports_filters 等）仍然存在，用于未来 P2/P3 的向量预筛选和匹配算法，但当前 Prompt 中不注入。

2.5 Summarize: 增加反编造规则

原始设计

summarize 仅负责格式化: 把工具返回的数据转成自然语言回答 + 表格/图表。

实际实现

summarize system prompt 加入 严格反编造规则: "只能基于提供的数据回答，绝对不能编造数据中没有的数字、百分比或结论。宁可说数据不足也不能给出没有依据的数字。"

为什么改：发现 LLM 会在总结时"发挥"，给出数据中不存在的百分比或对比结论。对企业系统来说，编造数据比说"不知道"严重得多。

2.6 变更汇总

维度 原始设计 实际实现 原因
ReAct 粒度 每轮一个工具，最多 4 轮 批量调用 + {{N.path}}，最多 3 次 think 减少 LLM 调用，追查过多有害
思考模板 自由 CoT 5 步结构化: 意图/候选/审查/规划/验证 自由 CoT 对工具选择不够甚至有害
观察注入 问"够不够"（是非判断） Reflexion: "有什么字段/缺什么"（事实陈述） 是非判断让 AI 倾向结束，事实陈述更客观
自学习 Verdict winner + LLM evaluate 代码存在但无效，等外部信号 AI 自评是循环论证
Guide EAM 查找表 (88%) 通用方法论 (90.6% with 级联) 查找表是作弊分，不可迁移
工具描述 YAML 全量元数据 标准 MCP: name + desc + params 自然语言链路关系更有效
级联策略 未设计 mini 失败 -> 5.4 重试（+16pp） 实验中发现的最大单一贡献
Summarize 纯格式化 加反编造规则 LLM 会编造不存在的数据

Part 3: 架构原则（今天确立的）

以下 7 条原则来自 2026-03-26 一整天的编码、benchmark、prompt 调优实验。不是理论猜测，是数据驱动的结论。

Principle 1
MCP 是动作，AI 是能力

MCP 工具负责"获取数据"（确定性操作），AI 负责"分析数据"（计数、分组、排序、Top-N、对比）。聚合/统计是 AI 的分析能力，不做成 MCP 工具。这是分工的边界。

Principle 2
Guide 是方法论，YAML 是具象化

tool-selection-guide.md 零项目特有内容，纯方法论。YAML 声明文件包含项目相关的域/描述/参数。guide 可以跨项目复用，YAML 跟着具体系统走。查找表式 guide 虽然准确率高 (88%)，但 28pp 差距是"作弊分"，不可迁移。

Principle 3
从错误中学习 > 记录正确答案

verdict（记 winner）在 60% 准确率下积累的是 40% 错误经验。AI 自评（lesson）是循环论证，同一个脑子犯的错自评也发现不了。有效学习信号必须来自外部: 用户反馈（thumbs down）、结果质量检测（空数据/字段不匹配）、Ground Truth（测试时）。

Principle 4
优化优先级: Prompt > AI 分析 > MCP

三个优化杠杆的实际贡献: (1) Prompt/AI 调度（5 步模板、级联、参数引用 -- 贡献 90%+）> (3) AI 分析能力（summarize 质量 -- 贡献需要数据支撑）> (2) MCP 工具质量（mock 优化是片面的，跑真实 API 前不值得深耕）。

Principle 5
工具应同时接受业务编号和内部 ID

Poka-yoke 原则: 用户说"EQ-001"时直接传 keyword，不强制先查出内部 ID 再传。减少一步查询，降低出错概率。工具描述中用自然语言嵌入链路关系（"list 工具不含 X，需要本工具补全"），比结构化的 feeds_into 更直接。

Principle 6
Summarize 绝对不能编造数据

对企业系统来说，编造数据比说"不知道"严重得多。summarize prompt 加入严格规则: 只能基于提供的数据回答，宁可说"数据不足"也不能给出没有依据的数字。

Principle 7
复杂度是输出不是输入

所有查询走同一条路径: 规划 -> 执行 -> 观察 -> 决定是否追查。不做"简单/复杂"预分类。实验证明: 扁平 94.2% > 分层 90.5%，多加一层判断只会引入新的错误。结果够了自然结束，不够自然追查。

Part 4: 自学习路线图（下一阶段）

4.1 当前状态

组件 状态 问题

4.2 下一步: 四条路径

路径 1: 结果质量检测（客观信号，最优先）

不依赖 AI 判断，纯粹检测工具返回的数据是否与用户问题匹配：

  • 空结果检测: 工具返回 items=[] 或 total=0，但用户问的是"有多少" -- 可能查错了工具或参数
  • 字段-意图不匹配: 用户问"备件库存"，但返回的数据里没有 stock/quantity 相关字段 -- 选错了工具
  • 数据-问题偏离: 用户问"A线设备"，但返回的数据里没有 productionLine=A 的记录
工具返回数据
  |
  v
[质量检测器] -- 纯规则，不用 LLM
  |
  +-- 空结果 + 用户问"有多少/哪些" --> 可能选错工具
  +-- 返回字段不含意图关键词        --> 可能选错工具
  +-- 数据匹配                      --> 正常，不操作
  |
  v (选错工具的情况)
自动生成 lesson:
  {
    intentHash: "...",
    query: "A线上月的备件消耗",
    selectedTools: ["query_equipment"],
    quality: "bad",
    errorReason: "返回设备列表但用户问的是备件消耗，字段不匹配",
    betterPath: [],  // 不猜测正确路径，留给下次 Prompt 注入时提醒 AI
    lesson: "查备件消耗不要用 query_equipment，它返回设备列表不含备件信息",
    source: "quality_check"
  }

路径 2: 用户反馈闭环

将已有的 Thumbs Down 连接到学习系统：

用户点 Thumbs Down
  |
  v
记录: session.feedback = "down" (已实现)
  |
  v
[新增] 从 session 中提取:
  query + selectedTools + resultSummary
  |
  v
写入 lesson:
  {
    query: "...",
    selectedTools: [...],
    quality: "bad",
    errorReason: "用户反馈不满意",
    source: "user_feedback"
  }
  |
  v
下次同类查询 (同 intentHash):
  Prompt 注入 lesson: "上次查询 X 选了 Y 工具但用户不满意，请换个方向"

路径 3: Ground Truth 注入（仅测试环境）

Benchmark 知道正确答案，可以自动为错误题注入 lesson：

benchmark 批跑
  |
  v
对比 AI 选择 vs Ground Truth
  |
  +-- 匹配 --> 跳过
  +-- 不匹配 --> 自动生成 lesson:
        {
          query: "...",
          selectedTools: [AI 选的],
          quality: "bad",
          errorReason: "应该选 [GT 的工具] 而不是 [AI 选的]",
          betterPath: [GT 工具链],
          source: "ground_truth"
        }
  |
  v
重跑 benchmark，验证 lesson 注入后准确率是否提升

注意: Ground Truth 本身需要审查（P1 发现 8 题 GT 跳过了 ID 解析步骤，比 AI 还差）。GT 注入只在测试环境使用，不进入生产。

路径 4: Skill 分解（架构升级）

将当前的单一 "think" 拆分为独立的可调优技能：

Skill 职责 独立 Prompt 独立评估
Intent Parsing 从自然语言提取结构化意图 专注意图理解，不看工具列表 意图标签准确率
Tool Selection 根据意图选择工具链 + 参数 专注工具匹配，输入是结构化意图 工具选择 Recall/Precision
Result Validation 检查工具返回是否回答了问题 专注事实对比，不做路由决策 异常检出率
Summarize 把数据转成用户可理解的回答 专注表达，反编造规则 回答质量评分

理论基础：基于 ToolGT（结构化模板）、Step-Back Prompting（先理解不看工具）、Reflexion（事实对比）三篇研究。当前的 5 步模板已经隐含了这个拆分，Skill 分解是把隐含结构变成显式模块，每个模块可以独立调优和评估。
