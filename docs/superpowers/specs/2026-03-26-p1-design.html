P1 Design — Insight68 NL-API Platform

目标：技术验证扩展能力。在 P0（22 MCP Tools, 94.2% 路由准确率）基础上深化智能层算法，为 P2 多系统规模化打基础。

方法论：先做最复杂的完整版（ReAct Agent），跑通后用减法验证哪些环节可以削减。

设计原则：对的时候准确，不确定的时候诚实。

1. 架构变化

P1 在 P0 的四层架构上做纵向深化，不改架构，增强智能层。

P0:  用户 → Prompt组装 → LLM一次路由 → 按序执行 → LLM总结 → 返回

P1:  用户 → Prompt组装(+记忆+verdict)
         → ReAct循环(思考→路由→执行→观察→再思考)
         → 结果自验证
         → LLM总结(+Grounding)
         → 置信度回退
         → 返回(+反馈按钮)

2. 模块清单（按依赖顺序）

#模块改动量核心产出
1会话层 + 经验层接入中router 真正读写 session/verdict
2ReAct Agent大替换单次路由，多轮推理循环
3自学习 verdict中冷启动 + 自动评估 + Thumbs Up/Down
4置信度回退 + 超纲识别中三信号真实计算，不再形同虚设
5结果自验证小数值合理性/空结果/单位一致性
6Grounding 标注小回答附带数据来源

不做的：持久层（用户偏好）— 对技术验证价值低，P2 再做。

3. 模块 1：会话层 + 经验层接入

现状

P0 的 SQLiteStorage 已建好 4 张表（sessions/verdicts/preferences/users），接口已定义，但 router 没有读写。

改动

  • router.ts：每次查询执行后，写入 nl_memory_sessions
  • router.ts：ReAct 开始前，读取同 intent_hash 的历史 session 作为上下文
  • router.ts：读取 verdict 作为推荐路径

不做

  • 持久层（preferences）不接
  • 用户表不接（P0 default tenant 够用）

4. 模块 2：ReAct Agent

核心循环（批量调用 + 按需追查）

用户查询 → [规划] 像 P0 一样一次规划完整工具链（可多个）
         → [批量执行] 按序执行所有工具调用
         → [观察] 结果够不够回答问题？
                  够 → 直接总结（和 P0 一样快）
                  不够 → [追查] 基于已有结果，补充新的工具调用
         → [批量执行] 执行补充调用
         → ... 最多 3 轮追查
         → [总结] 汇总所有结果，生成回答

设计决策

  • 最大追查轮次 = 3 — 第一轮规划 + 最多 3 轮追查。超过说明问题超纲或工具缺失，走置信度回退
  • 每轮可多个工具调用 — 第一轮和 P0 一样批量规划执行，简单查询零额外开销。追查轮基于已有结果补充调用
  • LLM 输出结构化 — 第一轮和追查轮格式统一，都可返回多个 calls：
// 第一轮：意图提取 + 工具链规划（和 P0 兼容）
{
  "thought": "用户想查A线上月故障最多的设备的备件库存，需要先查产线设备再查故障",
  "intent": {"domains": ["fault-repair", "spare"], "operation": "detail",
             "filters": ["productionLineId", "dateRange"]},
  "clarity": "clear",
  "calls": [
    {"tool": "query_equipment", "arguments": {"productionLineId": 1}},
    {"tool": "query_fault_reports", "arguments": {"dateRange": {"start": "2026-02-01", "end": "2026-02-28"}}}
  ]
}

// 追查轮：基于已有结果补充调用
{"thought": "已知 CNC-001 故障最多，需要查它的备件库存",
 "calls": [{"tool": "get_equipment_spare_bom", "arguments": {"equipmentId": 101}}]}

// 信息充足，结束
{"thought": "已有足够数据回答", "finish": true}

// 超纲
{"thought": "该问题超出系统能力范围", "finish": true, "unsupported": true}

第一轮的 intent 字段用于计算 intent_hash（SHA256(domains+operation+filters) 截取前 16 位），驱动 verdict 查找和 session 记录。clarity 字段直接输出置信度 queryClarity 信号。

  • 观察注入 — 上一步工具返回结果作为下一轮 Prompt 的一部分
  • JSON 校验 — 每轮用 zod schema 校验 LLM 输出，解析失败视为 finish with error

Prompt 组装策略

assemblePrompt() 仅在第一轮调用，生成包含完整工具清单和 ReAct 指令的 system prompt。后续每轮由 think() 方法内部追加 observation 消息，不重新组装 system prompt。

messages = [
  {role: "system", content: assemblePrompt()},         // 第一轮组装，后续不变
  {role: "assistant", content: JSON(turn1_output)},     // 第一轮输出
  {role: "user", content: "观察: " + JSON(tool_result)},// 工具结果
  {role: "assistant", content: JSON(turn2_output)},     // 第二轮输出
  ...
]

错误处理

级别场景处理
Level 1超时/网络错误作为 observation 注入，LLM 选择重试或替代
Level 2参数错误LLM 看到错误后调整参数
Level 3工具不存在标记 warning，LLM 选其他工具
Level 4MCP Server 不可用降级为 P0 线性模式

与 P0 兼容

简单查询（L1/L2）第一轮就 finish，不产生多余循环。复杂查询（L4/L5）才真正多轮。

think() 方法签名

interface ThinkResult {
  thought: string
  intent?: IntentTags          // 仅第一轮
  clarity?: ConfidenceLevel    // 仅第一轮
  calls?: ToolCall[]           // 本轮要执行的工具（可多个）
  finish?: boolean             // 结束
  unsupported?: boolean        // 超纲
}

think(messages: Array<{role: string, content: string}>): Promise<ThinkResult>

5. 模块 3：自学习 verdict 系统

数据流闭环

查询执行完成 → 异步写 session 日志
            → 累积同一 intent_hash 达 5 条 → 触发 verdict 计算
            → LLM 自动评分 (relevance×0.5 + completeness×0.3 + efficiency×0.2)
            → 计算 winner 工具链，写入 verdict 表
            → 下次同类查询，verdict 加分影响 ReAct 推荐路径

Thumbs Up/Down → 直接修正 verdict 分数（权重 = 3 条自动评估）

三阶段数据来源

阶段数据来源样本量
冷启动40 题测试集批跑40 条 session
自动积累每次查询异步评分持续增长
人工修正Thumbs Up/Down1 次 = 3 条自动

安全护栏

  • 只加分不减分（+25 medium / +50 high）
  • 上限 +50
  • 30 天自动过期
  • 人工可覆盖

与 ReAct 的集成

ReAct 每轮[思考]阶段，如果当前 intent_hash 有 verdict，把 winner 工具链作为"推荐路径"注入 Prompt。LLM 可以参考也可以忽略，不是硬编码。

Feedback 存储

Thumbs Up/Down 写入 nl_memory_sessions.feedback 字段（已有列，值为 "up" / "down" / null）。verdict 计算时，有 feedback 的 session 权重 ×3。不新建 feedback 表。

冷启动注意

40 题测试集可能只覆盖 15-20 个 distinct intent_hash，每个仅 1-2 条样本。解决：冷启动模式下降低阈值为 3 条，并为高频 intent 补充 2-3 条同义改写。

6. 模块 4：置信度回退 + 超纲识别

P0 现状

三信号写死（toolMatch=high, verdictConfidence=medium, queryClarity=high），形同虚设。

P1 — 三信号真实计算

信号计算方式
toolMatchReAct 第一轮 thought 中 LLM 自报确信度（P1 不启用 matchScore 预筛选）
verdictConfidence直接读 verdict 表（sample≥10=high, 3-9=medium, <3=low）
queryClarityReAct 第一轮意图提取时判断：明确/有歧义/超纲

超纲识别

融入 ReAct 第一轮[思考]。LLM 判断问题不在 22 个工具覆盖范围时，输出 unsupported: true。

回退策略：

  • high → 直接回答
  • medium → 回答 + 提示"以上是根据您的描述匹配的结果"
  • low → 给选项帮用户定位

7. 模块 5：结果自验证

工具执行后、LLM 总结前插入校验层。纯规则不用 LLM。

工具返回数据 → 自验证检查 → 通过 → 进入总结
                          → 异常 → 标记 warning，注入总结 Prompt
检查规则处理
数值合理性百分率 ∈ [0,100]、数量 ≥ 0、日期不在未来标红 + "数据可能异常"
空结果检测items=[] 或 total=0区分"确实没有" vs "可能查错了"
单位一致性简单关键词检测P1 不过度工程化

新增 lib/brain/validator.ts，纯函数，好测试。

8. 模块 6：Grounding 标注

类型扩展

interface StructuredResult {
  // ... 现有字段
  sources: Array<{ tool: string; description: string }>
}

ReAct 每轮执行工具时记录来源（工具名 + YAML 里的 description），最终汇总到 sources。

前端在回答下方显示灰色小字："数据来源：EAM 系统总览、故障报修记录"。

功能成功标准验证方式

全部用自动化脚本验证，不依赖人工判断。

10. 不做的（明确排除）

  • 持久层（用户偏好）— P2
  • 前端大改 — P1 只加 Thumbs Up/Down 和 Grounding 小字
  • 多系统接入 — P2
  • 向量预筛选 — P2（工具数 < 30 不需要）
  • 写操作 — P1 只读

11. 技术风险

风险缓解
ReAct 循环增加延迟简单查询第一轮就 finish；设最大轮次 5
LLM 自评 verdict 自嗨Thumbs Up/Down 人工信号修正，权重 3×
codex-proxy 不稳定每轮设 30s 超时，失败降级为 P0 线性模式
LLM 输出格式不稳定zod schema 校验每轮输出，解析失败视为 finish with error

延迟目标

查询类型目标
L1/L2（1 轮 finish）< 3s
L3（2-3 轮）< 6s
L4/L5（4-5 轮）< 12s

超过 3s 的查询前端显示进度提示（"正在分析..."/"正在查询第 N 步数据..."）。

12. 与 platform-design.md 的差异

P1 用 ReAct 模式替换了 platform-design.md Section 5.7 的 __continue__ 哨兵机制。ReAct 更显式（每步有 thought 可观测）、更灵活（LLM 基于观察自主决策）。实施时同步更新 platform-design.md Section 5.7。
